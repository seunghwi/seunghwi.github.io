쇼핑몰에 상품이 수백만 개 있다고 가정해봅시다. 상품 번호로 상세 정보를 찾고, “방수 등산화”로 상품을 검색하고, 이번 달 매출을 집계해야 합니다. 모두 저장된 정보를 읽는 작업이지만, 빨라지는 방법은 서로 다릅니다.

상품 번호 조회에는 데이터베이스 인덱스가, 반복되는 상세 조회에는 캐시가, 상품명과 설명 검색에는 Elasticsearch 같은 검색 엔진이 잘 맞을 수 있습니다. 대량 매출 집계에는 열 단위 저장이나 미리 계산한 집계표가 유리할 수 있습니다.

핵심은 **찾으려는 질문에 맞춰 데이터를 저장하고, 조회할 때 읽거나 계산할 양을 줄이는 것**입니다. 이 글에서는 제품 이름을 나열하는 데서 나아가, 각 방식이 어떻게 저장하고 왜 빠르게 찾는지 살펴봅니다.

## 빠른 조회를 만드는 기본 원리

책에서 특정 내용을 찾을 때 첫 페이지부터 끝까지 읽을 수도 있지만, 색인에서 단어를 찾으면 필요한 페이지로 바로 갈 수 있습니다. 자주 찾는 페이지를 책갈피로 표시하거나, 중요한 내용을 별도 표로 정리하는 방법도 있습니다.

데이터 시스템도 비슷한 방법을 조합합니다.

| 방법 | 미리 준비하는 것 | 조회할 때 줄어드는 일 |
|---|---|---|
| 인덱스 | 값과 데이터 위치를 연결한 탐색 구조 | 관련 없는 행 읽기 |
| 캐시 | 자주 사용하는 값이나 계산 결과의 사본 | 원본 조회·반복 계산 |
| 역색인 | 단어별로 그 단어가 있는 문서 목록 | 모든 문서의 본문 검사 |
| 열 단위 저장 | 같은 열의 값을 모은 구조 | 필요 없는 열 읽기 |
| 사전 집계 | 합계·건수 등 계산된 결과 | 같은 집계 반복 |
| 벡터 인덱스 | 비슷한 벡터를 찾기 위한 탐색 구조 | 모든 벡터와 거리 비교 |
| 그래프 구조 | 개체 사이의 관계 | 연결 관계를 반복해서 찾아 조합하기 |

이 과정에는 대가도 있습니다. 인덱스를 만들고 유지하는 시간, 사본을 저장할 공간, 갱신 지연과 운영 복잡성이 추가됩니다. 읽기를 빠르게 만들기 위해 저장·쓰기·동기화 단계에서 일을 더 하는 경우가 많습니다.

## 1. 관계형 DB 인덱스: 정렬된 길을 따라 필요한 행으로 이동한다

### 어떤 제품이 있을까?

대표적인 제품은 **PostgreSQL**과 **MySQL**입니다. 회원, 주문, 결제처럼 구조화된 정보를 저장하고 조건으로 조회하는 작업에서 출발점이 됩니다.

관계형 DB라고 해서 물리적으로 모두 똑같이 저장하지는 않습니다. 예를 들어 MySQL의 InnoDB는 클러스터 인덱스의 리프에 행 데이터를 저장하고, 보조 인덱스에는 기본 키 값을 포함합니다. 보조 인덱스로 찾은 뒤 기본 키로 실제 행을 찾아갈 수 있습니다. 구조는 [InnoDB 인덱스 문서](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)에 설명되어 있습니다.

### 어떻게 빨리 찾을까?

많이 사용하는 **B-tree 계열 인덱스**는 정렬된 키를 트리 형태로 관리합니다. 전화번호부에서 이름 범위를 좁히듯, 찾는 값이 있을 구간으로 내려갑니다.

~~~text
회원 번호 42의 최근 주문을 찾는다

전체 검사:
모든 주문 → 회원 번호 검사 → 결과 정렬 → 20개 선택

질의에 맞는 인덱스:
회원 42의 인덱스 구간으로 이동 → 최신 순서로 읽기 → 20개 선택
~~~

B-tree는 값이 정확히 같은 조건뿐 아니라 날짜·가격의 범위와 정렬에도 활용할 수 있습니다. 모든 질의가 같은 인덱스로 빨라지는 것은 아닙니다. PostgreSQL은 배열 등의 요소 검색에 쓰는 GIN, 물리적 데이터 순서와 상관관계가 높은 열의 블록 범위를 요약하는 BRIN 등도 제공합니다. [PostgreSQL 인덱스 종류](https://www.postgresql.org/docs/current/indexes-types.html)에서 각 용도를 비교할 수 있습니다.

### 인덱스는 질문의 모양에 맞춰 만든다

다음은 `orders` 테이블에 `id`, `customer_id`, `created_at`, `total_amount` 열이 있다고 가정한 PostgreSQL 예시입니다.

~~~sql
CREATE INDEX idx_orders_customer_created
ON orders (customer_id, created_at DESC);

SELECT id, created_at, total_amount
FROM orders
WHERE customer_id = 42
ORDER BY created_at DESC
LIMIT 20;
~~~

`customer_id`로 범위를 좁히고 그 안에서 생성 시각 순서로 읽도록 설계한 것입니다. 이처럼 여러 열로 만든 것을 **복합 인덱스**라고 합니다. 선두 열의 조건은 읽을 범위를 줄이는 데 중요합니다. 실제 활용 방식은 조건과 데이터 분포, DB의 최적화 기능에 따라 달라집니다. [복합 인덱스 공식 문서](https://www.postgresql.org/docs/current/indexes-multicolumn.html)를 참고할 수 있습니다.

인덱스를 추가했다고 반드시 빨라지는 것은 아닙니다. 대부분의 행을 읽어야 하는 질의는 전체를 순차적으로 읽는 편이 나을 수 있습니다. 인덱스 자체도 공간을 차지하고 삽입·수정·삭제 때 갱신해야 하므로, 자주 쓰는 질의를 기준으로 선택해야 합니다.

성능을 확인할 때는 실행 계획과 실제 읽은 양을 봅니다. PostgreSQL에서는 `EXPLAIN`으로 계획을, `EXPLAIN (ANALYZE, BUFFERS)`로 실행 결과와 버퍼 사용을 확인할 수 있습니다. `ANALYZE` 옵션은 쿼리를 실제로 실행한다는 점을 구분해야 합니다. [EXPLAIN 사용법](https://www.postgresql.org/docs/current/using-explain.html)에 자세한 설명이 있습니다.

## 2. 캐시: 이미 구한 답을 가까운 곳에서 다시 꺼낸다

### 캐시는 제품 종류이면서 사용 방식이기도 하다

**캐시(cache)**는 원본에서 다시 얻거나 계산할 수 있는 값을 사본으로 보관해 재사용하는 방식입니다. 별도 캐시 서버뿐 아니라 애플리케이션 메모리, 브라우저, CDN, DB 내부 버퍼에도 캐시가 있습니다.

흔히 “캐시 DB”라고 부르는 제품에는 **Redis**, **Valkey**, **Memcached**가 있습니다. 하지만 Redis나 Valkey를 사용한다고 모든 데이터가 자동으로 캐시가 되는 것은 아닙니다. 그 데이터가 원본인지, 원본에서 재생성하는 사본인지에 따라 역할이 달라집니다.

| 제품 | 저장 방식과 특징 | 대표적인 사용 |
|---|---|---|
| Redis | 메모리 중심 키-값 저장소, 문자열·해시·집합·정렬 집합 등 자료구조 | 조회 결과 캐시, 카운터, 순위 등 |
| Valkey | 메모리 중심 키-값 저장소, 다양한 자료구조와 영속화 기능 | 캐시와 데이터 구조 기반 처리 |
| Memcached | 키에 대응하는 값을 저장하는 메모리 캐시 | 직렬화한 객체나 조회 결과의 단순 캐싱 |

각 제품의 기능은 [Redis 자료구조 안내](https://redis.io/docs/latest/develop/get-started/data-store/), [Valkey 소개](https://valkey.io/topics/introduction/), [Memcached 사용 가이드](https://docs.memcached.org/userguide/)에서 확인할 수 있습니다. 제품과 버전별 기능이 같다고 가정해서는 안 됩니다.

### 어떻게 저장하고 찾을까?

상품 상세 결과를 JSON 문자열로 직렬화하고, 상품 번호를 포함한 키로 저장한다고 가정해봅시다. 다음은 Redis CLI에서 사용하는 명령 예시입니다.

~~~text
SET product:123 '{"id":123,"name":"방수 등산화","price":89000}' EX 60
GET product:123
~~~

`EX 60`은 60초의 만료 시간을 설정합니다. 다음 요청은 `product:123`이라는 키로 값을 가져옵니다. Redis의 문자열 `GET`은 키 조회 관점에서 O(1) 명령으로 정의되어 있습니다. 다만 큰 값을 전송하고 해석하는 시간, 네트워크 지연까지 일정하다는 뜻은 아닙니다. [SET](https://redis.io/docs/latest/commands/set/)과 [GET](https://redis.io/docs/latest/commands/get/) 문서에서 동작을 확인할 수 있습니다.

이때 빠른 이유는 메모리를 사용하기 때문만이 아닙니다. 여러 테이블을 조인하거나 JSON을 다시 구성하는 작업을 이미 끝낸 결과를 꺼내기 때문이기도 합니다.

반대로 위 JSON을 넣었다고 해서 `GET`으로 “가격 10만 원 이하의 방수 등산화”를 검색할 수 있는 것은 아닙니다. 기본 키 조회는 키를 알아야 합니다. 별도의 검색 기능이나 자료구조를 쓰지 않는 한 값 내부의 조건을 자동으로 인덱싱해주지 않습니다.

### 캐시에 없을 때는 어떻게 할까?

자주 사용하는 **Cache-Aside** 흐름은 다음과 같습니다.

~~~text
상품 상세 요청
  → 캐시에서 product:123 조회
       ├─ 있음: 저장된 값 반환                  [캐시 히트]
       └─ 없음: 원본 DB 조회                    [캐시 미스]
                 → 결과를 캐시에 만료 시간과 함께 저장
                 → 결과 반환
~~~

캐시에 처음 접근하거나 데이터가 만료되면 원본을 조회해야 합니다. 이때는 캐시 조회 비용까지 추가되므로, **반복 조회가 충분히 많고 원본 조회 비용이 클 때** 효과가 커집니다. 이 방식과 일관성의 한계는 [Microsoft의 Cache-Aside 패턴](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside)에 설명되어 있습니다.

### 빠르지만 오래된 값을 보여줄 수 있다

원본 상품 가격을 수정해도 기존 캐시가 자동으로 바뀌는 것은 아닙니다. 원본 갱신 후 해당 키를 삭제하거나, 새 값을 반영하는 정책이 필요합니다. 만료 시간인 **TTL**은 사본의 수명을 제한하지만 원본과 항상 같음을 보장하지 않습니다.

특히 동시에 조회와 갱신이 일어나면 키를 삭제한 직후 다른 요청이 오래된 결과를 다시 채울 수 있습니다. 일관성 요구가 높으면 버전 검증, 갱신 이벤트 처리 등 추가 설계가 필요합니다. 재고 차감이나 결제 확정은 캐시 화면 값만으로 판단하지 않고 원본의 일관성 있는 처리 경로에서 검증해야 합니다.

캐시가 한꺼번에 만료되어 요청들이 동시에 원본으로 몰리는 현상도 있습니다. 같은 키의 재계산을 하나로 합치거나, TTL에 작은 무작위 차이를 두는 방법을 검토할 수 있습니다.

메모리 부족으로 키를 제거하는 **축출(eviction)**은 시간 만료와 다른 동작입니다. 정책에 따라 만료 전에도 캐시가 사라질 수 있습니다. [Redis 축출 정책](https://redis.io/docs/latest/develop/reference/eviction/)을 참고해 캐시 미스가 정상적으로 처리되도록 설계해야 합니다.

### 메모리 저장소면 재시작할 때 전부 잃을까?

Redis는 스냅샷 방식의 RDB와 변경 명령을 기록하는 AOF 등 영속화 선택지를 제공합니다. 복구 가능한 시점과 성능 비용은 설정에 따라 달라집니다. 메모리 중심이라는 말과 디스크에 전혀 저장하지 않는다는 말은 같지 않습니다. [Redis 영속화 문서](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)에서 차이를 확인할 수 있습니다.

캐시라면 손실 후 재생성이 가능하도록 설계하고, 원본 저장소로 쓴다면 복구·백업·장애 시 데이터 손실 범위를 별도로 따져야 합니다.

## 3. Elasticsearch: 단어에서 문서로 가는 색인을 만든다

### 어떤 정보를 저장할까?

**Elasticsearch**는 JSON 문서를 저장하고 검색·분석하는 엔진입니다. 상품, 게시글, 로그를 각각 문서로 표현할 수 있습니다.

~~~json
{
  "product_id": "P123",
  "name": "방수 등산화",
  "description": "비 오는 날 산행에 적합한 신발",
  "category": "등산화",
  "price": 89000
}
~~~

문서는 **인덱스(index)**라는 논리적 저장 단위에 들어갑니다. 여기서 인덱스는 관계형 DB의 보조 인덱스와 정확히 같은 의미가 아닙니다. 문서들의 집합을 다루는 단위이며 내부에는 다양한 검색용 자료구조가 만들어집니다.

필드의 자료형과 처리 방식을 정하는 **매핑(mapping)**도 중요합니다. 일반적으로 본문처럼 분석할 문자열에는 `text`, 상품 코드나 분류처럼 정확한 값으로 다룰 문자열에는 `keyword`, 가격에는 숫자 자료형을 사용합니다. 저장 구조는 [Elasticsearch 인덱스 기초](https://www.elastic.co/docs/manage-data/data-store/index-basics)에 설명되어 있습니다.

### 역색인은 문서의 목차를 뒤집은 구조다

다음은 원리를 보여주는 가상 데이터입니다. 실제 분석기의 토큰화 결과는 아닙니다.

~~~text
원본 문서
문서 1: 방수 등산화
문서 2: 경량 등산화
문서 3: 방수 재킷

역색인
방수   → [문서 1, 문서 3]
등산화 → [문서 1, 문서 2]
경량   → [문서 2]
재킷   → [문서 3]
~~~

“방수”와 “등산화”를 모두 포함하는 문서를 찾는다면 두 목록의 교집합인 문서 1을 찾을 수 있습니다. 모든 문서 본문을 처음부터 읽는 대신, 검색어에 대응하는 문서 목록으로 후보를 좁히는 것입니다. 이 단어별 목록을 **포스팅 리스트(postings list)**라고 부릅니다.

이처럼 **단어 → 문서** 방향으로 만든 구조가 **역색인(inverted index)**입니다. 반면 가격 정렬이나 집계는 문서별 필드 값을 읽어야 하므로 다른 접근이 필요합니다. Elasticsearch는 이 용도로 열 지향 구조인 **doc values** 등을 사용합니다. [doc values 공식 문서](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/doc-values)는 두 접근의 차이를 설명합니다.

### 한국어 검색에서는 어떻게 단어를 나눌지도 중요하다

검색 엔진은 문장을 토큰으로 나누고 정규화하는 **분석기(analyzer)**를 사용합니다. 색인 시점과 검색 시점의 분석 결과가 잘 맞아야 원하는 문서가 검색됩니다. 대소문자, 동의어와 단어 형태 처리도 관련됩니다. [텍스트 분석 문서](https://www.elastic.co/docs/manage-data/data-store/text-analysis)를 참고할 수 있습니다.

한국어에서는 조사, 복합명사, 띄어쓰기를 어떻게 다룰지가 검색 품질에 영향을 줍니다. Elasticsearch의 한국어 분석 도구로 [Nori 플러그인](https://www.elastic.co/docs/reference/elasticsearch/plugins/analysis-nori)이 있습니다. 적용 전에 실제 상품명과 사용자 검색어를 분석해 결과를 확인하는 편이 좋습니다.

여기서 토큰은 검색에 사용할 조각입니다. LLM의 토큰과 용어는 같지만 목적과 분할 규칙이 같다는 뜻은 아닙니다.

### 일치한 문서를 어떤 순서로 보여줄까?

검색은 후보를 찾는 것뿐 아니라 관련 있는 결과를 위에 놓는 일도 포함합니다. Elasticsearch의 기본 텍스트 유사도 방식인 **BM25**는 단어 빈도, 문서 길이, 단어의 희소성 등을 반영해 점수를 계산합니다. [유사도 설정 문서](https://www.elastic.co/docs/reference/elasticsearch/index-settings/similarity)를 참고할 수 있습니다.

이 점수는 사용자의 구매 의도나 사실 여부를 완벽하게 판정하는 값은 아닙니다. 상품명에 높은 가중치를 주거나, 분류·가격 필터를 적용하거나, 의미 검색을 결합하는 등 서비스에 맞는 조정이 필요합니다.

### 저장 직후 검색되지 않을 수 있다

Elasticsearch는 **준실시간(near real-time)** 검색을 제공합니다. 쓰기가 완료된 시점과 새 문서가 검색에 보이는 시점 사이에는 refresh에 따른 차이가 생길 수 있습니다. 구체적인 설정과 동작은 [준실시간 검색 문서](https://www.elastic.co/docs/manage-data/data-store/near-real-time-search)에 설명되어 있습니다.

원본 DB에서 검색 엔진으로 데이터를 복사한다면, 여기에 전달 지연까지 더해집니다. 그래서 상품 검색에서는 검색 엔진을 사용하더라도, 주문 확정 시 가격과 재고는 원본 처리 경로에서 다시 확인하는 식으로 역할을 나눌 수 있습니다.

### 비슷한 제품은 무엇이 있을까?

**OpenSearch**도 문서 검색과 로그 분석 등에 사용하는 검색·분석 제품입니다. 역색인 기반 텍스트 검색이라는 공통점이 있지만 Elasticsearch와 기능·API·플러그인이 계속 동일하다고 가정해서는 안 됩니다. [OpenSearch 소개](https://docs.opensearch.org/latest/getting-started/intro/)에서 지원 범위를 확인할 수 있습니다.

관계형 DB에도 전문 검색이나 특수 인덱스가 있습니다. 검색 규모와 요구가 작다면 기존 DB의 기능으로 해결 가능한지 먼저 검토하고, 검색 품질 조정이나 독립적인 확장이 필요할 때 별도 검색 엔진을 고려할 수 있습니다.

## 4. 열 단위 저장과 사전 집계: 대량 통계에 필요한 것만 읽는다

### ClickHouse: 같은 열을 모아서 저장한다

“이번 달 지역별 매출 합계”는 주문 한 건을 빨리 찾는 것과 다릅니다. 많은 행을 읽고 더해야 하므로, **얼마나 적은 바이트를 읽고 효율적으로 계산하는가**가 중요합니다.

**ClickHouse** 같은 열 지향 분석 DB는 같은 열의 값을 모아서 저장합니다. 날짜, 지역, 금액만 필요한 질의에서 배송 주소나 상품 설명 같은 다른 열을 읽는 부담을 줄일 수 있습니다. 비슷한 값이 모여 압축에도 유리합니다.

~~~text
행 중심의 개념적 배치
[날짜, 지역, 금액, 주소] [날짜, 지역, 금액, 주소] ...

열 중심의 개념적 배치
날짜: [날짜, 날짜, 날짜, ...]
지역: [지역, 지역, 지역, ...]
금액: [금액, 금액, 금액, ...]
주소: [주소, 주소, 주소, ...]
~~~

ClickHouse의 MergeTree 계열은 정렬된 데이터 파트와 희소 인덱스 등을 활용해 관련 없는 구간을 건너뛰도록 합니다. 기본 키 인덱스가 모든 행을 가리키는 구조는 아니며, 관계형 DB의 기본 키처럼 유일성을 강제하지도 않습니다. [MergeTree 공식 문서](https://clickhouse.com/docs/reference/engines/table-engines/mergetree-family/mergetree)를 참고할 수 있습니다.

열 지향 저장은 대량 분석에 유리한 방식입니다. 그렇다고 개별 주문의 빈번한 수정이나 결제 트랜잭션까지 모두 더 적합하다는 뜻은 아닙니다.

### 물리화 뷰: 계산 결과를 저장한다

매번 수천만 건을 합산하는 대신 날짜별 매출을 미리 계산해 저장할 수도 있습니다. 대표적인 방법이 **물리화 뷰(materialized view)**입니다.

PostgreSQL의 일반 뷰는 조회 정의를 저장하지만, 물리화 뷰는 결과를 테이블 같은 형태로 보관합니다. 조회 시 원본 전체를 다시 계산하지 않아도 되지만 새 결과를 반영하려면 갱신이 필요합니다. [PostgreSQL 물리화 뷰 문서](https://www.postgresql.org/docs/current/rules-materializedviews.html)에 설명되어 있습니다.

~~~text
원본 주문 수천만 건
  → 날짜·지역별 매출 계산
  → 집계 결과 저장
  → 대시보드는 작은 집계 결과 조회
~~~

캐시와 마찬가지로 결과를 재사용하지만, 조회 정의와 갱신 방식이 DB 기능으로 관리된다는 차이가 있습니다. 다른 제품의 물리화 뷰는 갱신 방식이 다를 수 있으므로 이름만 보고 동작이 같다고 판단해서는 안 됩니다.

## 5. 벡터와 그래프: 단어 일치나 값 비교로 부족할 때

### 벡터 검색: 의미가 가까운 후보를 찾는다

“비 오는 날 산에서 신을 신발”이라는 질문으로 “방수 등산화”를 찾고 싶다면, 단어 일치 외에 의미의 유사성을 활용할 수 있습니다.

문서와 질문을 임베딩 모델로 숫자 벡터로 변환하고, 가까운 벡터를 찾습니다. **Qdrant** 같은 벡터 DB나 PostgreSQL 확장인 **pgvector**가 대표적인 선택지입니다.

HNSW 같은 근사 최근접 이웃 인덱스는 모든 벡터와 거리를 비교하는 대신 유망한 후보를 탐색합니다. 속도를 얻는 대신 실제로 가장 가까운 항목 일부를 놓칠 수 있어, 검색 품질과 지연 시간을 함께 측정해야 합니다. 구조와 옵션은 [Qdrant 인덱싱 문서](https://qdrant.tech/documentation/manage-data/indexing/)와 [pgvector 공식 문서](https://github.com/pgvector/pgvector)에서 확인할 수 있습니다.

벡터 검색이 가격 범위나 상품 코드의 정확한 일치를 대신하는 것은 아닙니다. 메타데이터 필터나 키워드 검색과 조합하는 경우가 많습니다.

### 그래프 조회: 저장된 연결을 따라간다

“이 고객과 같은 기기를 사용한 계정이 어떤 결제 수단을 공유하는가?”처럼 관계를 여러 단계 따라가야 한다면 그래프 모델이 유용합니다.

**Neo4j**는 개체를 노드로, 연결을 관계로 저장하고 속성을 붙이는 그래프 DB입니다. 시작 노드를 찾은 뒤 관계를 따라 탐색하는 방식으로 질문을 표현할 수 있습니다. 데이터 모델은 [Neo4j 그래프 개념](https://neo4j.com/docs/getting-started/appendix/graphdb-concepts/)에서 확인할 수 있습니다.

그래프라고 모든 탐색이 빠른 것은 아닙니다. 연결이 매우 많거나 깊이 제한 없이 탐색하면 후보가 폭증할 수 있습니다. 관계 모델, 시작 조건과 탐색 범위를 설계해야 합니다.

두 방식은 기존 글인 [벡터 DB와 그래프 DB: 차이점과 활용 상황]({% post_url 2026-09-04-vector-database-and-graph-database %})에서 더 자세히 다뤘습니다.

## 실제 서비스에서는 어떻게 함께 사용할까?

쇼핑몰을 예로 들면 다음과 같은 역할 분담을 생각할 수 있습니다. 아래는 필요할 때 확장하는 설계 예시이며, 모든 서비스에 이 제품을 전부 도입하라는 뜻은 아닙니다.

~~~text
사용자 요청 → 애플리케이션
                ├─ 상품 번호 조회 → 캐시 → 미스 시 원본 DB
                ├─ 상품 검색      → 검색 엔진
                ├─ 주문 확정      → 원본 DB에서 가격·재고 검증
                └─ 통계 화면      → 분석 DB 또는 집계 결과

원본 변경 → 변경 이벤트 → 검색용 문서 갱신
                       → 캐시 무효화 또는 갱신
                       → 분석용 데이터 반영
~~~

여기서 **원본 DB를 수정한다고 다른 저장소가 자동으로 일치하지는 않습니다.** 변경 이벤트, CDC(Change Data Capture), 주기적 동기화 등 전달 경로를 설계해야 합니다.

실무에서는 다음 조건을 함께 정하는 것이 좋습니다.

- **기준 데이터**: 문제가 생겼을 때 어느 저장소의 값을 기준으로 복구할지 정합니다.
- **최신성**: 검색과 통계가 원본보다 얼마나 늦어도 되는지 정합니다.
- **재처리**: 이벤트가 누락·중복되거나 순서가 바뀌어도 복구할 수 있어야 합니다.
- **재구축**: 캐시가 비거나 검색 인덱스를 새로 만들 때의 절차를 준비합니다.
- **격리**: 사용자·조직별 데이터가 섞이지 않도록 캐시 키와 검색 필터에 접근 범위를 반영합니다.

동일 데이터를 여러 군데 저장하면 조회 방식은 유연해지지만, 그 사본을 맞추는 일이 새로운 작업이 됩니다.

## 파티셔닝과 서버 증설은 언제 도움이 될까?

**파티셔닝**은 데이터를 날짜나 키 범위 등으로 나누는 방식입니다. 날짜 조건으로 이번 달 데이터만 필요하다면 이전 달 파티션을 읽지 않을 수 있습니다. 하지만 조건이 분할 기준과 맞지 않으면 여러 파티션을 모두 읽어야 합니다. [PostgreSQL 파티셔닝 문서](https://www.postgresql.org/docs/current/ddl-partitioning.html)는 이런 파티션 가지치기를 설명합니다.

여러 서버에 데이터를 나누는 **샤딩**과 복제본 추가도 목적이 다릅니다. Elasticsearch에서 샤드는 데이터를 분할하고, 복제본은 장애 대응과 읽기 부하 분산에 활용됩니다. 검색이 여러 샤드로 퍼지면 각 결과를 모으는 비용도 생깁니다. [Elasticsearch 저장 구조](https://www.elastic.co/docs/manage-data/data-store/index-basics)를 참고할 수 있습니다.

따라서 서버를 늘리면 동시에 처리할 요청 수가 개선될 수는 있어도, 잘못된 조회 방식의 단일 요청 시간이 자동으로 줄어드는 것은 아닙니다. 먼저 읽는 양과 실행 경로를 확인하는 편이 좋습니다.

## 무엇부터 선택하면 좋을까?

다음은 제품의 절대적인 우열이 아니라, 앞의 원리를 적용한 검토 순서입니다.

1. **실제 질문을 적습니다.** 키 조회, 범위 검색, 전문 검색, 반복 조회, 대량 집계를 구분합니다.
2. **현재 병목을 측정합니다.** DB 실행 계획, 읽은 행·바이트 수, 네트워크와 애플리케이션 계산 시간을 확인합니다.
3. **기존 DB에서 줄일 수 있는 일을 찾습니다.** 질의·인덱스·읽는 열을 조정하고 필요하면 집계를 검토합니다.
4. **반복 조회가 많으면 캐시를 검토합니다.** 히트율뿐 아니라 만료·갱신·장애 시 원본 부하를 함께 봅니다.
5. **질문 자체가 다르면 맞는 저장 방식을 추가합니다.** 본문 검색은 검색 엔진, 대량 분석은 열 지향 DB, 의미 검색은 벡터 인덱스가 후보입니다.
6. **실제 데이터로 비교합니다.** 평균뿐 아니라 느린 요청 구간인 p95·p99 지연 시간, 쓰기 성능, 최신성, 운영 비용을 함께 측정합니다.

“캐시를 넣으니 몇 배 빨라졌다”는 결과도 같은 조건에서 확인해야 합니다. 캐시가 비어 있을 때와 채워졌을 때, 반복되는 요청과 새로운 요청, 한 명이 사용할 때와 동시에 몰릴 때는 결과가 다를 수 있습니다.

빠른 조회를 설계할 때 가장 먼저 할 질문은 **“어떤 제품이 빠른가?”보다 “이 요청에서 읽거나 다시 계산하지 않아도 되는 것은 무엇인가?”**입니다. 그 답에 맞는 인덱스, 사본, 검색 구조를 준비하면 제품을 선택하는 이유도 분명해집니다.
