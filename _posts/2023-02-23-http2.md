HTTP/2는 HTTP의 의미를 바꾸지 않고, 메시지를 전송하는 방식을 더 효율적으로 설계한 프로토콜입니다. 요청 메서드와 상태 코드, URI, 헤더의 의미는 그대로 유지하면서 데이터를 **바이너리 프레임**으로 나누고, 하나의 TCP 연결에서 여러 요청과 응답을 동시에 처리합니다.

이 글은 현재 HTTP/2 표준인 [RFC 9113](https://www.rfc-editor.org/rfc/rfc9113.html)을 기준으로 연결 수립부터 프레임, 스트림, 흐름 제어와 헤더 압축까지 살펴봅니다. 최초 표준이었던 RFC 7540은 2022년에 RFC 9113으로 대체되었습니다.

## 한눈에 보는 HTTP/2

HTTP/2의 구조는 다음 세 단위로 이해하면 쉽습니다.

1. **연결(Connection)**: 클라이언트와 서버 사이에 맺은 하나의 TCP 연결
2. **스트림(Stream)**: 하나의 요청과 응답이 오가는 독립적인 양방향 흐름
3. **프레임(Frame)**: HTTP/2에서 실제로 전송되는 가장 작은 프로토콜 단위

하나의 연결에는 여러 스트림이 존재할 수 있고, 각 스트림은 하나 이상의 프레임으로 구성됩니다.

~~~text
TCP 연결
├─ Stream 1: HEADERS → DATA → DATA
├─ Stream 3: HEADERS → DATA
└─ Stream 5: HEADERS → DATA → DATA
~~~

![HTTP/2 연결, 스트림, 프레임 구조](/images/20230223/http2.png)

각 프레임에는 자신이 속한 스트림의 ID가 기록됩니다. 따라서 서로 다른 요청의 프레임이 한 연결 안에서 섞여 전송되어도 수신 측에서 다시 올바른 스트림으로 조립할 수 있습니다.
{: .notice--info}

## HTTP/2가 등장한 이유

HTTP/1.1은 한 TCP 연결에서 여러 요청을 순차적으로 처리할 수 있지만, 앞선 응답이 지연되면 뒤의 응답도 기다려야 하는 애플리케이션 계층의 **Head-of-Line Blocking** 문제가 있습니다. 브라우저는 이를 완화하기 위해 같은 서버에 여러 TCP 연결을 생성해 병렬 요청을 처리해 왔습니다.

하지만 연결 수가 늘어나면 TCP와 TLS 핸드셰이크 비용이 반복되고, 서버와 클라이언트가 관리해야 할 자원도 증가합니다. HTTP/2는 Google의 SPDY에서 얻은 경험을 바탕으로 다음 기능을 표준화했습니다.

- 바이너리 프레이밍
- 스트림 다중화
- 스트림과 연결 단위의 흐름 제어
- HPACK을 이용한 헤더 압축
- 요청 우선순위 전달
- 서버 푸시

핵심은 HTTP의 기능을 새로 정의한 것이 아니라, **동일한 HTTP 메시지를 더 효율적으로 운반하는 계층을 만든 것**입니다.

## 연결은 어떻게 시작되는가

HTTP/2는 TCP 위에서 동작하는 연결 지향 애플리케이션 프로토콜입니다. 실무에서는 대부분 HTTPS와 함께 사용합니다.

### HTTPS 연결

클라이언트는 TLS 핸드셰이크의 ALPN(Application-Layer Protocol Negotiation) 확장에서 지원 프로토콜을 제시합니다. 서버가 HTTP/2를 선택하면 ALPN 식별자 **<code>h2</code>**가 사용됩니다. 협상이 끝난 뒤부터 HTTP/2 프레임을 주고받습니다.

### 암호화되지 않은 연결

명세상 평문 HTTP/2도 가능하지만, 클라이언트가 서버의 지원 여부를 미리 알고 있어야 합니다. 이를 흔히 **prior knowledge 방식의 h2c**라고 부릅니다. 과거 RFC 7540에 있던 HTTP/1.1 Upgrade 방식은 RFC 9113에서 폐기되었습니다.

따라서 “HTTP/2는 반드시 TLS를 사용한다”는 설명은 명세 관점에서는 정확하지 않습니다. 다만 일반 웹 환경에서는 브라우저와 서버의 호환성 및 보안을 위해 HTTPS가 사실상 기본입니다.
{: .notice--warning}

### Connection Preface와 SETTINGS

프로토콜이 결정되면 양쪽은 HTTP/2 연결을 확인하고 초기 설정을 교환합니다.

1. 클라이언트가 24바이트의 고정 문자열 <code>PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n</code>을 전송합니다.
2. 이어서 클라이언트의 <code>SETTINGS</code> 프레임을 전송합니다.
3. 서버는 첫 프레임으로 자신의 <code>SETTINGS</code> 프레임을 전송합니다.
4. 양쪽은 상대의 설정을 적용하고 ACK 플래그가 지정된 <code>SETTINGS</code> 프레임으로 확인합니다.

<code>SETTINGS</code>에는 최대 동시 스트림 수, 초기 흐름 제어 윈도 크기, 최대 프레임 크기, 서버 푸시 허용 여부 같은 연결 단위 옵션이 포함될 수 있습니다.

## 바이너리 프레임

HTTP/1.1 메시지는 시작 줄과 헤더를 텍스트로 표현하지만, HTTP/2는 모든 메시지를 바이너리 프레임으로 직렬화합니다. 모든 프레임은 고정된 **9바이트 헤더**와 가변 길이 payload로 구성됩니다.

~~~text
+-----------------------------------------------+
|                 Length (24)                   |
+---------------+---------------+---------------+
|   Type (8)    |   Flags (8)   |
+-+-------------+---------------+-------------------------------+
|R|                 Stream Identifier (31)                      |
+=+=============================================================+
|                   Frame Payload (0...)                      ...
+---------------------------------------------------------------+
~~~

| 필드 | 크기 | 의미 |
|---|---:|---|
| Length | 24비트 | 9바이트 헤더를 제외한 payload 길이 |
| Type | 8비트 | DATA, HEADERS, SETTINGS 등 프레임 종류 |
| Flags | 8비트 | END_STREAM, END_HEADERS, ACK 등 타입별 옵션 |
| R | 1비트 | 예약 비트이며 송신 시 0으로 설정 |
| Stream Identifier | 31비트 | 프레임이 속한 스트림 ID. 0은 연결 제어용 |
| Frame Payload | 가변 | 타입에 따라 달라지는 실제 데이터 |

기본 최대 프레임 payload 크기는 16,384바이트입니다. 수신 측이 <code>SETTINGS_MAX_FRAME_SIZE</code>로 더 큰 값을 알리면 최대 16,777,215바이트까지 확장할 수 있습니다. 프레임 타입 자체에 별도 크기 제한이 있는 경우에는 그 제한도 지켜야 합니다.

### 주요 프레임 타입

| 프레임 | 역할 |
|---|---|
| <code>DATA</code> | 요청 또는 응답의 본문을 전달 |
| <code>HEADERS</code> | HPACK으로 압축된 헤더 필드를 전달하고 스트림을 시작 |
| <code>CONTINUATION</code> | 하나의 헤더 블록이 프레임 하나에 들어가지 않을 때 이어서 전달 |
| <code>SETTINGS</code> | 연결에 적용할 설정을 교환 |
| <code>WINDOW_UPDATE</code> | 스트림 또는 연결의 흐름 제어 윈도를 증가 |
| <code>RST_STREAM</code> | 특정 스트림을 즉시 종료 |
| <code>PING</code> | 연결 생존 여부와 왕복 시간을 확인. ACK 응답도 PING 프레임을 사용 |
| <code>GOAWAY</code> | 새 스트림 수신을 중단하고 연결 종료를 준비 |
| <code>PUSH_PROMISE</code> | 서버가 생성할 스트림을 클라이언트에 미리 알림 |
| <code>PRIORITY</code> | RFC 7540의 우선순위 신호. 현재 표준에서는 사용 중단 권고 |

<code>END_HEADERS</code>는 헤더 블록이 끝났음을, <code>END_STREAM</code>은 해당 송신 방향에서 더 보낼 데이터가 없음을 뜻합니다. 두 플래그는 역할이 다르므로 구분해야 합니다.

## 스트림과 다중화

스트림은 하나의 요청과 응답을 운반하는 독립적인 양방향 채널입니다. 클라이언트가 시작한 스트림은 홀수 ID를, 서버가 시작한 스트림은 짝수 ID를 사용합니다. 스트림 ID 0은 <code>SETTINGS</code>, <code>PING</code>, <code>GOAWAY</code>처럼 연결 전체를 제어하는 프레임에 사용됩니다.

예를 들어 클라이언트가 세 요청을 동시에 보내면 프레임은 다음처럼 교차할 수 있습니다.

~~~text
→ HEADERS(stream=1)  GET /index.html
→ HEADERS(stream=3)  GET /app.css
→ HEADERS(stream=5)  GET /app.js
← HEADERS(stream=3)  200
← DATA   (stream=3)
← HEADERS(stream=1)  200
← DATA   (stream=1)
← HEADERS(stream=5)  200
← DATA   (stream=5)
~~~

스트림 3의 응답이 먼저 완료되어도 스트림 1과 5의 순서를 기다릴 필요가 없습니다. 이것이 HTTP/2 다중화의 핵심입니다. 단, **같은 스트림 안의 프레임 순서**는 의미가 있으므로 유지해야 합니다.

### 스트림 상태

스트림의 수명 주기는 다음 상태로 관리됩니다.

| 상태 | 의미 |
|---|---|
| <code>idle</code> | 아직 생성되지 않은 상태 |
| <code>reserved (local)</code> | 로컬 endpoint가 서버 푸시용으로 예약 |
| <code>reserved (remote)</code> | 상대 endpoint가 서버 푸시용으로 예약 |
| <code>open</code> | 양쪽 모두 프레임을 송신할 수 있는 상태 |
| <code>half-closed (local)</code> | 로컬 송신은 끝났지만 상대의 프레임은 받을 수 있는 상태 |
| <code>half-closed (remote)</code> | 상대 송신은 끝났지만 로컬에서는 프레임을 보낼 수 있는 상태 |
| <code>closed</code> | 양쪽 송수신이 모두 끝난 상태 |

일반적인 GET 요청은 다음과 같이 전이됩니다.

~~~text
idle
  └─ 클라이언트가 HEADERS + END_STREAM 전송
       └─ half-closed (local)
            └─ 서버가 HEADERS와 DATA + END_STREAM 전송
                 └─ closed
~~~

요청 본문이 있다면 먼저 <code>open</code> 상태에서 DATA를 주고받고, 한쪽이 <code>END_STREAM</code>을 보내면 해당 방향만 닫힙니다. <code>RST_STREAM</code>은 정상 완료를 기다리지 않고 스트림을 <code>closed</code> 상태로 전환합니다.

## 흐름 제어

다중화된 연결에서는 빠른 송신자가 느린 수신자의 버퍼를 가득 채우지 않도록 제어해야 합니다. HTTP/2는 다음 두 수준에 각각 흐름 제어 윈도를 둡니다.

- **스트림 윈도**: 특정 요청이나 응답이 사용할 수 있는 용량
- **연결 윈도**: 연결에 속한 모든 스트림이 함께 사용할 수 있는 전체 용량

초기 윈도 크기는 둘 다 65,535바이트입니다. 송신자는 DATA를 보낼 때 스트림 윈도와 연결 윈도를 모두 차감하고, 둘 중 하나라도 부족하면 추가 전송을 멈춥니다. 수신자가 데이터를 처리한 뒤 <code>WINDOW_UPDATE</code>를 보내면 송신 가능한 크기가 다시 늘어납니다.

HTTP/2에서 흐름 제어를 적용받는 기본 프레임은 <code>DATA</code>뿐입니다. <code>SETTINGS</code>나 <code>PING</code>, <code>WINDOW_UPDATE</code> 같은 제어 프레임까지 막히면 연결이 교착 상태에 빠질 수 있기 때문입니다.
{: .notice--info}

이 흐름 제어는 최종 클라이언트와 원 서버 사이 전체 경로가 아니라, 클라이언트-프록시 또는 프록시-서버처럼 **한 홉의 HTTP/2 연결별로 독립적으로 동작**합니다.

## HPACK 헤더 압축

HTTP 요청에는 <code>user-agent</code>, <code>accept</code>, <code>cookie</code>처럼 여러 요청에서 반복되는 헤더가 많습니다. HTTP/2는 [RFC 7541](https://www.rfc-editor.org/rfc/rfc7541.html)에 정의된 **HPACK**으로 헤더 블록을 압축합니다.

HPACK은 세 가지 방식을 조합합니다.

- 자주 사용되는 헤더 이름과 값을 미리 정의한 **정적 테이블**
- 현재 연결에서 반복되는 값을 저장하는 **동적 테이블**
- 문자열 자체를 줄이는 선택적 **허프먼 코딩**

한 번 동적 테이블에 저장된 헤더는 이후 인덱스만 전송할 수 있어 반복 비용이 크게 줄어듭니다. 단, 양쪽의 동적 테이블 상태가 일치해야 하므로 헤더 블록을 해석하지 못하면 해당 스트림만이 아니라 연결 전체의 <code>COMPRESSION_ERROR</code>가 됩니다.

인증 정보처럼 민감한 값은 동적 테이블에 남지 않도록 “never indexed” 표현을 사용할 수 있습니다. 압축 효율뿐 아니라 테이블 크기 제한과 민감 정보 처리도 구현 시 중요한 요소입니다.

## HTTP 메시지는 어떻게 표현되는가

HTTP/2는 요청 줄과 상태 줄을 그대로 전송하지 않습니다. 대신 이름이 콜론으로 시작하는 **의사 헤더(pseudo-header)**로 제어 정보를 표현합니다.

HTTP/1.1 요청을 보면 다음과 같습니다.

~~~http
GET /resource?id=1 HTTP/1.1
Host: example.com
Accept: application/json
~~~

동일한 의미의 HTTP/2 헤더 블록은 다음과 같이 표현됩니다.

~~~text
:method: GET
:scheme: https
:authority: example.com
:path: /resource?id=1
accept: application/json
~~~

요청에는 일반적으로 <code>:method</code>, <code>:scheme</code>, <code>:authority</code>, <code>:path</code>가 사용되고, 응답에는 상태 코드를 담은 <code>:status</code>가 사용됩니다. 의사 헤더는 일반 헤더보다 먼저 위치해야 하며 같은 이름을 중복해서 전송할 수 없습니다.

~~~text
:status: 200
content-type: application/json
content-length: 17
~~~

헤더는 <code>HEADERS</code> 프레임으로, 본문은 하나 이상의 <code>DATA</code> 프레임으로 전달됩니다. HTTP/1.1의 <code>Transfer-Encoding: chunked</code>는 사용할 수 없으며, 스트림의 끝은 <code>END_STREAM</code> 플래그로 표현합니다. 또한 <code>Connection</code>, <code>Keep-Alive</code>, <code>Proxy-Connection</code>, <code>Transfer-Encoding</code>, <code>Upgrade</code>처럼 연결에 종속된 헤더는 HTTP/2 메시지에 포함할 수 없습니다.

## 우선순위와 서버 푸시

RFC 7540은 스트림 의존성과 가중치를 이용하는 복잡한 우선순위 모델을 정의했지만 구현 일관성이 낮았습니다. 현재 RFC 9113은 이 방식을 사용 중단하도록 권고합니다. 새로운 방식은 [RFC 9218](https://www.rfc-editor.org/rfc/rfc9218.html)의 <code>Priority</code> 헤더와 <code>PRIORITY_UPDATE</code> 프레임으로 긴급도와 점진적 처리 여부를 전달합니다.

서버 푸시는 클라이언트가 요청하지 않은 리소스를 서버가 미리 보내는 기능입니다. 서버는 <code>PUSH_PROMISE</code>로 예정된 스트림을 알리지만, 클라이언트는 <code>SETTINGS_ENABLE_PUSH=0</code>으로 푸시를 거부하거나 <code>RST_STREAM</code>으로 개별 푸시를 취소할 수 있습니다.

두 기능 모두 프로토콜에 정의되어 있다는 사실과 실제 제품에서 적극적으로 사용된다는 것은 별개입니다. 성능 최적화 시에는 브라우저와 서버 구현의 지원 상태를 함께 확인해야 합니다.

## 오류 처리와 연결 종료

HTTP/2는 오류 범위를 구분합니다.

- **스트림 오류**: 특정 요청만 실패합니다. 일반적으로 <code>RST_STREAM</code>으로 종료합니다.
- **연결 오류**: 프레이밍이나 압축 상태처럼 연결 전체를 신뢰할 수 없는 문제입니다. <code>GOAWAY</code>를 보내고 연결을 종료합니다.

대표적인 오류 코드는 다음과 같습니다.

| 코드 | 값 | 의미 |
|---|---:|---|
| <code>NO_ERROR</code> | <code>0x0</code> | 정상 종료 |
| <code>PROTOCOL_ERROR</code> | <code>0x1</code> | 프로토콜 규칙 위반 |
| <code>INTERNAL_ERROR</code> | <code>0x2</code> | 구현 내부 오류 |
| <code>FLOW_CONTROL_ERROR</code> | <code>0x3</code> | 흐름 제어 규칙 위반 |
| <code>SETTINGS_TIMEOUT</code> | <code>0x4</code> | SETTINGS 확인 시간 초과 |
| <code>STREAM_CLOSED</code> | <code>0x5</code> | 닫힌 스트림에 허용되지 않은 프레임 수신 |
| <code>FRAME_SIZE_ERROR</code> | <code>0x6</code> | 프레임 크기 규칙 위반 |
| <code>REFUSED_STREAM</code> | <code>0x7</code> | 처리 전에 스트림 거부 |
| <code>CANCEL</code> | <code>0x8</code> | 스트림 취소 |
| <code>COMPRESSION_ERROR</code> | <code>0x9</code> | HPACK 상태 또는 디코딩 오류 |
| <code>CONNECT_ERROR</code> | <code>0xa</code> | CONNECT로 만든 연결 오류 |
| <code>ENHANCE_YOUR_CALM</code> | <code>0xb</code> | 상대가 과도한 부하를 유발 |
| <code>INADEQUATE_SECURITY</code> | <code>0xc</code> | 필요한 보안 조건을 충족하지 못함 |
| <code>HTTP_1_1_REQUIRED</code> | <code>0xd</code> | 해당 요청에 HTTP/1.1이 필요함 |

<code>GOAWAY</code>에는 처리했을 가능성이 있는 마지막 스트림 ID가 포함됩니다. 클라이언트는 그보다 큰 ID의 요청이 처리되지 않았다고 판단해 새 연결에서 재시도할 수 있습니다. 이 구조 덕분에 서버는 연결을 갑자기 끊지 않고 점진적으로 종료할 수 있습니다.

## HTTP/2가 해결하지 못한 것

HTTP/2는 애플리케이션 계층에서 스트림 간 대기를 줄였지만 여전히 하나의 TCP 바이트 스트림 위에서 동작합니다. 패킷이 유실되면 TCP가 손실된 데이터를 복구할 때까지 같은 연결의 모든 HTTP/2 스트림이 영향을 받을 수 있습니다. 이를 **전송 계층의 Head-of-Line Blocking**이라고 합니다.

또한 다중화 자체가 항상 성능 향상을 보장하지는 않습니다. 흐름 제어 윈도, 서버의 스케줄링, 네트워크 지연과 손실률, 과도한 동시 스트림 수에 따라 결과가 달라집니다. HTTP/2를 사용할 때도 측정에 기반한 튜닝이 필요합니다.

## 정리

HTTP/2의 핵심은 다음과 같습니다.

1. HTTP의 의미는 유지하고 전송 형식을 바이너리 프레임으로 변경합니다.
2. 요청과 응답마다 스트림 ID를 부여해 하나의 TCP 연결에서 다중화합니다.
3. 스트림과 연결 단위 흐름 제어로 수신자의 처리 능력을 보호합니다.
4. HPACK으로 반복되는 헤더 전송량을 줄입니다.
5. 스트림 오류와 연결 오류를 구분해 실패 범위를 제어합니다.
6. 애플리케이션 계층의 대기는 줄이지만 TCP 계층의 Head-of-Line Blocking은 남아 있습니다.

프레임은 전송 단위이고, 스트림은 요청과 응답의 논리적 통로이며, 연결은 여러 스트림을 함께 운반하는 기반입니다. 이 세 계층의 관계를 이해하면 HTTP/2의 나머지 동작도 자연스럽게 연결됩니다.
