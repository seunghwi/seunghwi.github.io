AI 서비스를 사용하다 보면 “입력 토큰”, “최대 출력 토큰”, “컨텍스트 한도”라는 표현을 만납니다. 가격표에도 토큰이 등장하다 보니 요금을 계산하기 위한 단위로만 생각하기 쉽습니다.

하지만 토큰은 그보다 근본적인 역할을 합니다. **토큰은 언어 모델이 글을 입력받고, 학습하고, 답변을 생성할 때 사용하는 기본 단위입니다.** 문맥 길이나 비용의 단위로 쓰이는 것도 이 처리 과정과 연결되어 있습니다.

[앞선 글]({% post_url 2026-09-07-ai-learning-inference-and-effective-prompts %})에서는 AI의 학습과 추론을 살펴봤습니다. 이번 글에서는 텍스트를 생성하는 대규모 언어 모델(LLM)을 중심으로, 토큰이 각 단계에서 정확히 어떤 일을 하는지 알아봅니다.

## 토큰은 글을 처리하기 위해 나눈 조각이다

사람은 문장을 읽을 때 단어와 의미를 자연스럽게 파악합니다. 언어 모델에 글을 넣을 때는 먼저 **토크나이저(tokenizer)**가 텍스트를 정해진 규칙에 따라 나눕니다. 그 결과로 얻는 조각이 토큰입니다.

토큰은 단어 전체일 수도 있고, 단어의 일부나 문장부호일 수도 있습니다. 공백이 뒤따르는 단어와 한 토큰으로 묶이기도 합니다. 바이트 기반 방식에서는 토큰 하나가 화면에 보이는 글자 하나보다 작은 조각에 대응할 수도 있습니다.

따라서 다음 세 가지를 구분해야 합니다.

| 단위 | 무엇을 세는가? | 토큰과의 관계 |
|---|---|---|
| 글자 | 사람이 글자로 인식하는 것 또는 프로그램이 정한 문자 단위 | 토큰과 일대일 대응하지 않음 |
| 단어·어절 | 언어적 기준이나 띄어쓰기로 구분한 말 | 하나가 여러 토큰이 될 수 있음 |
| 토큰 | 해당 토크나이저가 구분한 처리 단위 | 모델에 전달되는 시퀀스의 단위 |

토큰을 “의미의 최소 단위”라고 외우면 오해가 생깁니다. 토크나이저는 반드시 문법적 의미나 형태소 경계에 맞춰 자르지 않습니다. 어떤 조각은 그 자체로 사람이 이해할 만한 뜻이 없을 수 있습니다. 토큰의 기본 정의는 [Google의 언어 모델 입문 자료](https://developers.google.com/machine-learning/crash-course/llm)에서 확인할 수 있습니다.

### 왜 단어 단위나 글자 단위로만 나누지 않을까?

단어마다 별도 항목을 만들면 신조어, 이름, 활용형까지 다루기 위해 목록이 매우 커집니다. 반대로 글자 하나씩 나누면 목록은 작아지지만, 같은 문장을 처리하는 데 필요한 조각 수가 길어집니다.

많은 토크나이저는 이 사이에서 **서브워드(subword)**라는 단어보다 작은 조각을 활용합니다. 자주 쓰이는 표현은 크게 묶고, 드문 표현은 더 작은 조각으로 표현할 수 있습니다.

대표 방식인 **BPE(Byte Pair Encoding)**는 토크나이저를 학습할 때 자주 함께 나타나는 인접 조각을 합쳐 어휘와 병합 규칙을 만듭니다. **Unigram**, **WordPiece**처럼 다른 방식도 있습니다. 구체적인 차이는 [Hugging Face의 토큰화 알고리즘 문서](https://huggingface.co/docs/transformers/tokenizer_summary)에 정리되어 있습니다.

여기서 토크나이저의 규칙을 학습하는 것과, 언어 모델의 가중치를 학습하는 것은 구분해야 합니다. 일반적인 서비스 이용 중에는 이미 정해진 토크나이저로 입력을 변환합니다.

## 역할 1: 글을 모델이 계산할 수 있는 입력으로 바꾼다

토큰은 사람의 글과 모델의 숫자 계산을 연결하는 출발점입니다. 보통 다음 단계를 거칩니다.

~~~text
사용자의 글
  → 토크나이저가 조각으로 분리
  → 각 조각에 대응하는 토큰 ID
  → ID에 대응하는 임베딩 벡터
  → 모델 내부 계산
~~~

### 토큰 ID는 조각을 찾기 위한 번호다

토크나이저는 **어휘 집합(vocabulary)**을 가지고 있습니다. 이는 사용할 토큰과 번호를 연결한 목록입니다. 각 토큰에 대응하는 정수 번호를 **토큰 ID**라고 부릅니다.

아래는 원리를 설명하기 위해 만든 가상 예시입니다. 실제 모델의 분할 결과나 ID가 아닙니다.

~~~text
원문:       오늘은 맑다.
가상 분할: [오늘] [은] [ 맑] [다] [.]
가상 ID:   [ 41,  87,  215,  19,  6 ]
~~~

여기서 `215`라는 숫자가 `41`보다 더 중요하거나 더 강한 의미를 갖는 것은 아닙니다. 단순히 서로 다른 항목을 가리키는 번호입니다.

같은 글이라도 토크나이저가 다르면 분할 결과와 ID가 달라질 수 있습니다. 한 모델의 토큰 ID를 다른 모델에 그대로 넣으면 같은 뜻이 전달된다고 가정할 수 없습니다. 모델에 맞는 토크나이저를 사용해야 합니다. 이 변환 과정은 [Hugging Face의 Tokenizers 강의](https://huggingface.co/learn/llm-course/en/chapter2/4)에서 설명합니다.

### 임베딩은 계산에 사용하는 숫자 배열이다

모델은 ID 자체의 크기를 의미로 해석하지 않습니다. 일반적인 구조에서는 ID로 **임베딩(embedding)** 표의 해당 행을 찾아 여러 숫자로 이루어진 벡터를 가져옵니다.

| 구분 | 역할 | 비유 |
|---|---|---|
| 토큰 | 텍스트를 구성하는 조각 | 부품 |
| 토큰 ID | 조각을 구별하는 번호 | 부품 번호 |
| 임베딩 벡터 | 모델 계산에 사용하는 표현 | 계산에 쓰는 부품의 수치 정보 |

즉, 토큰과 임베딩은 같은 것이 아닙니다. 토큰은 구분한 단위이고, 임베딩은 그 단위를 계산에 사용할 수 있도록 표현한 벡터입니다.

## 역할 2: 문맥 속 관계를 계산하는 위치가 된다

토큰을 숫자로 바꾸는 것만으로 문맥이 이해되는 것은 아닙니다. 모델은 **어떤 토큰이 어떤 순서로 놓여 있는지, 다른 토큰과 어떻게 연결되는지**를 계산해야 합니다.

예를 들어 다음 문장을 비교해봅시다.

~~~text
강아지가 사람을 따라갔다.
사람이 강아지를 따라갔다.
~~~

비슷한 표현이 들어 있어도 누가 누구를 따라갔는지는 다릅니다. 그래서 트랜스포머 계열 모델은 토큰 표현과 함께 위치 정보를 활용합니다. 위치 정보를 넣는 구체적인 방법은 모델마다 다릅니다.

또한 **어텐션(attention)**은 각 위치에서 다른 위치의 정보를 얼마나 반영할지 계산합니다. 이 관계 계산과 다른 신경망 연산을 여러 층에서 반복하면, 처음의 토큰 임베딩은 문맥을 반영한 내부 표현으로 바뀝니다.

같은 토큰 ID라도 주변 내용이 달라지면 내부 표현이 달라질 수 있다는 뜻입니다. 토큰 하나에 고정된 사전적 의미만 붙여 문장을 해석하는 구조로 이해해서는 안 됩니다. 임베딩, 위치 정보와 어텐션의 기본 구조는 [Attention Is All You Need](https://arxiv.org/abs/1706.03762)에서 다룹니다.

사용자 관점에서는 “이것을 고쳐줘”의 **이것**이 무엇인지 분명하게 주는 것이 중요합니다. 모델은 전달된 문맥의 관계를 계산하므로, 대상 문서나 코드가 빠져 있으면 내가 의도한 연결을 확실히 알 수 없습니다.

## 역할 3: 학습에서 예측하고 평가하는 단위가 된다

텍스트 생성 모델의 대표적인 학습 방식은 **앞의 토큰들을 보고 다음 토큰을 예측하는 것**입니다.

토큰 배열을 `t1, t2, t3, t4`라고 하면 다음과 같은 관계를 학습합니다.

~~~text
앞에 주어진 토큰    예측해야 할 다음 토큰
t1                 t2
t1, t2             t3
t1, t2, t3         t4
~~~

모델은 어휘 집합의 후보들에 점수를 계산하고, 이를 확률 분포로 바꿉니다. 실제 다음 토큰에 얼마나 높은 확률을 주었는지를 바탕으로 **손실(loss)**을 계산합니다. 대표적으로 사용하는 교차 엔트로피 손실은 정답 토큰에 낮은 확률을 줄수록 커집니다.

이 손실을 줄이도록 가중치를 조정하는 과정을 많은 자료에서 반복합니다. 토큰은 이때 **입력 단위인 동시에 예측 목표와 오차 계산의 단위**가 됩니다. 구현 예시는 [Hugging Face의 인과적 언어 모델 학습 강의](https://huggingface.co/learn/llm-course/en/chapter7/6)에서 볼 수 있습니다.

이 표는 학습 목표를 설명한 것입니다. 실제 트랜스포머 학습에서는 미래 토큰을 보지 못하도록 마스크를 적용하면서 여러 위치의 예측을 병렬로 계산할 수 있습니다. 학습도 반드시 한 토큰씩 순서대로 실행해야 한다는 뜻은 아닙니다.

학습 데이터가 “몇 조 토큰”이라는 표현은 이러한 단위로 데이터 양을 센 것입니다. 그만큼의 서로 다른 사실을 배웠다는 뜻은 아닙니다. 같은 문장이나 비슷한 내용이 반복될 수도 있고, 데이터의 품질도 별개입니다.

## 역할 4: 답변을 생성하고 끝내는 단위가 된다

사용자가 질문하면 모델은 일반적으로 앞의 입력을 바탕으로 다음 토큰을 예측합니다. 선택한 토큰을 기존 입력 뒤에 붙이고 다시 다음 토큰을 예측하는 과정을 반복합니다. 이를 **자기회귀 생성(autoregressive generation)**이라고 합니다.

~~~text
질문과 이전 대화
  → 다음 토큰 후보 계산
  → 생성 방식에 따라 토큰 하나 선택
  → 선택한 토큰을 뒤에 추가
  → 다음 토큰 후보 계산
  → 종료 조건까지 반복
  → 토큰 ID 배열을 텍스트로 디코딩
~~~

토큰 ID 배열을 다시 사람이 읽는 글로 바꾸는 과정을 **디코딩(decoding)**이라고 합니다. 생성 문맥에서는 후보 중 다음 토큰을 고르는 전략도 디코딩 전략이라고 부르므로, 두 용례를 구분하면 문서를 읽기 쉽습니다.

항상 확률이 가장 높은 토큰만 고르는 것은 아닙니다. 확률에 따라 후보를 선택하는 샘플링 등 여러 방법이 있습니다. 구체적인 생성 방식과 종료 설정은 [Hugging Face의 텍스트 생성 문서](https://huggingface.co/docs/transformers/llm_tutorial)에 설명되어 있습니다.

### 답변이 끝났다는 것도 표시가 필요하다

어휘에는 일반 글 조각 외에 **특수 토큰(special token)**이 포함될 수 있습니다. 모델에 따라 시퀀스의 시작이나 끝, 메시지 경계 등을 표시합니다. 대표적인 종료 표시는 **EOS(End of Sequence)**입니다.

시스템은 종료 토큰, 최대 생성 길이 또는 별도의 중단 조건에 따라 생성을 멈출 수 있습니다. 그래서 출력 한도에 걸려 잘린 답변과 모델이 정상적으로 마친 답변은 구분해야 합니다.

화면에 글이 조금씩 나타나는 스트리밍도 이런 생성과 연결됩니다. 다만 화면으로 전달되는 조각 하나가 항상 토큰 하나는 아닙니다. 서버나 화면이 여러 토큰을 모아서 표시할 수 있습니다.

### 토큰을 잘 예측하는 것과 사실 확인은 다르다

다음 토큰의 확률은 **주어진 문맥에서 그 토큰이 이어질 확률**입니다. 완성된 문장의 사실 여부를 직접 보증하는 숫자는 아닙니다.

예를 들어 자연스러운 보고서 문장을 만들면서 실제 자료에 없는 매출액을 생성할 수도 있습니다. 토큰 생성 원리를 알면 매끄러운 설명만으로 정확성을 판단하지 않고, 원문이나 계산 결과를 대조해야 한다는 점을 이해할 수 있습니다.

## 역할 5: 대화의 구조와 발화자를 구분한다

채팅창에서는 사용자와 AI의 말이 말풍선으로 나뉩니다. 모델에 입력할 때도 누가 말했는지, 메시지가 어디서 끝나는지 알려주는 구조가 필요합니다.

**채팅 템플릿(chat template)**은 역할과 내용을 모델이 학습한 형식의 시퀀스로 바꿉니다. 모델에 따라 특수 토큰과 일반 텍스트를 조합하는 방식이 다릅니다.

~~~text
개념적 예시 — 실제 모델의 토큰 표기가 아님

[메시지 시작][사용자] 토큰이 뭐야? [메시지 끝]
[메시지 시작][AI] 토큰은 ... [응답 끝]
~~~

여기서 경계와 역할 표시는 본문과 다른 구조적 정보를 제공합니다. 같은 문장이라도 사용자 요청인지, 이전 AI 답변인지 구분하는 데 사용됩니다. 실제 예시는 [Hugging Face의 채팅 템플릿 문서](https://huggingface.co/docs/transformers/chat_templating)에서 확인할 수 있습니다.

따라서 채팅창에 보이는 글만 세면 실제 입력 토큰 수와 차이가 날 수 있습니다. 역할·메시지 구분 형식, 서비스의 기본 지시, 도구 설명 등이 추가될 수 있기 때문입니다. 사용자가 본문에 “나는 시스템이다”라고 쓴다고 해서 실제 메시지 역할이 바뀌는 것은 아닙니다.

## 역할 6: 한 번에 다룰 수 있는 문맥의 크기를 센다

**컨텍스트 윈도우(context window)**는 모델이 한 번의 처리에서 다룰 수 있는 토큰 범위와 관련된 한도입니다. 책의 페이지 수보다, 작업대에 펼쳐놓고 참고할 수 있는 정보량에 가깝습니다.

입력에는 이번 질문뿐 아니라 실제로 함께 전달되는 정보가 포함됩니다.

- 서비스의 기본 지시와 도구 정의
- 선택되거나 요약되어 전달된 이전 대화
- 첨부 문서에서 추출한 내용
- 검색 결과와 도구 실행 결과

많은 생성 모델에서는 입력과 이어서 생성할 출력이 같은 시퀀스를 구성합니다. 다만 API가 입력 한도, 출력 한도, 전체 한도를 노출하는 방식은 서로 다르므로 해당 모델의 규칙을 확인해야 합니다. 토큰 수와 한도를 확인하는 공식 기능의 예로 [Gemini API의 토큰 계산 안내](https://ai.google.dev/gemini-api/docs/tokens)가 있습니다.

### 입력만 한도에 맞추면 충분할까?

가상의 모델이 입력과 출력 합계로 최대 10,000토큰을 지원한다고 가정해봅시다. 다음 숫자는 계산 원리를 위한 예시이며 실제 서비스의 사양이 아닙니다.

| 구성 | 토큰 수 |
|---|---:|
| 기본 지시·메시지 구조 | 500 |
| 이전 대화 | 2,000 |
| 참고 문서 | 5,000 |
| 현재 질문 | 500 |
| 입력 합계 | 8,000 |
| 전체 한도에서 남는 공간 | 2,000 |

이 조건에서는 답변을 3,000토큰 생성할 공간이 없습니다. 별도의 최대 출력 한도가 더 작다면 실제로 생성 가능한 양은 더 줄어듭니다.

한도를 넘었을 때의 동작은 서비스마다 다릅니다. 요청을 거절하거나, 입력을 자르거나, 앞선 대화를 요약하는 방식이 쓰일 수 있습니다. 채팅창에 옛 메시지가 남아 있다는 것과 모델이 이번 답변에서 그 원문 전체를 보고 있다는 것은 별개입니다.

### 문맥이 길면 모든 정보를 잘 활용할까?

입력할 수 있는 양과 필요한 정보를 정확히 활용하는 능력도 구분해야 합니다. [Lost in the Middle](https://arxiv.org/abs/2307.03172)은 실험 대상 모델이 긴 입력에서 정보의 위치에 따라 성능 차이를 보였다고 보고합니다. 모든 모델에 같은 결과를 적용할 수는 없지만, 큰 입력 한도만으로 완벽한 기억을 기대해서는 안 된다는 점을 보여줍니다.

실무에서는 자료를 무조건 많이 붙이기보다 관련 부분을 고르고, 제목과 출처를 표시하고, 현재 작업의 확정 조건을 짧게 정리하는 편이 좋습니다. 중요한 내용이 빠지지 않았는지는 별도로 확인해야 합니다.

## 역할 7: 처리 시간·메모리·사용 비용과 연결된다

토큰은 고정된 양의 연산을 뜻하지는 않습니다. 같은 1,000토큰이어도 모델 크기, 구조, 하드웨어, 입력과 출력의 구성에 따라 처리 비용이 달라집니다. 그래도 처리할 시퀀스의 길이를 나타내므로 자원 사용량과 밀접하게 연결됩니다.

### 입력을 읽는 과정과 출력을 만드는 과정은 다르다

생성 모델의 추론은 보통 입력을 처리하는 **프리필(prefill)**과, 그 뒤 새 토큰을 생성하는 **디코드(decode)** 단계로 나누어 설명합니다.

- **프리필**: 입력 토큰들을 처리하고 다음 생성에 필요한 내부 상태를 준비합니다.
- **디코드**: 앞서 처리한 내용과 생성 결과를 활용해 새 토큰을 이어서 만듭니다.

일반적인 자기회귀 생성에서는 다음 출력을 만들려면 앞에서 선택한 출력이 필요합니다. 따라서 같은 총 토큰 수라도 긴 입력을 읽는 경우와 긴 답변을 만드는 경우의 체감 속도가 다를 수 있습니다.

많은 구현은 이전 토큰의 어텐션 계산에 필요한 키와 값 벡터를 **KV 캐시**에 저장해 재사용합니다. 매번 전부 다시 계산하는 부담을 줄이지만, 문맥이 길어지면 캐시 메모리 부담도 커질 수 있습니다. 슬라이딩 윈도우 등 구조에 따라 양상은 달라집니다. 자세한 원리는 [Hugging Face의 캐시 설명](https://huggingface.co/docs/transformers/cache_explanation)을 참고할 수 있습니다.

### 입력 토큰과 출력 토큰을 따로 보는 이유

API는 입력·출력에 서로 다른 단가를 적용하거나 캐시된 입력을 별도로 계산할 수 있습니다. 모델에 따라 내부 추론에 사용한 토큰이 사용량에 포함되기도 하므로, 화면에 보이는 답변 길이만으로 전체 사용량을 판단하면 안 됩니다. 실제 항목은 [Gemini API 가격표](https://ai.google.dev/gemini-api/docs/pricing)처럼 사용하는 서비스의 공식 안내에서 확인해야 합니다.

캐시나 추가 과금 항목이 없는 단순한 가상 요금제라면 다음처럼 계산할 수 있습니다.

~~~text
입력 요금 = 입력 토큰 수 ÷ 1,000,000 × 입력 100만 토큰당 단가
출력 요금 = 출력 토큰 수 ÷ 1,000,000 × 출력 100만 토큰당 단가
총요금    = 입력 요금 + 출력 요금
~~~

이 식은 요금 구조를 설명하기 위한 것입니다. 웹 검색, 도구 호출, 캐시 저장 등 다른 항목이 있으면 추가 계산이 필요합니다. 채팅 서비스의 월 구독료와 API의 토큰 종량제도 같은 체계라고 가정해서는 안 됩니다.

또한 대화 기록을 매 요청에 다시 보내는 구조라면 이전 메시지도 새 요청의 입력으로 계산됩니다. “오늘 새로 입력한 문장만큼만 비용이 든다”는 식으로 생각하면 실제 사용량과 차이가 날 수 있습니다.

## 한국어와 이미지도 같은 방식으로 셀 수 있을까?

### 한국어는 글자 수로 고정 환산하지 않는다

한국어는 조사와 어미가 결합하고, 같은 표현도 띄어쓰기나 표기에 따라 달라집니다. 토크나이저의 어휘와 규칙에 따라 잘리는 위치도 달라집니다.

따라서 “한글 한 글자는 무조건 몇 토큰”이라는 공식을 쓰면 안 됩니다. 특정 모델에서는 같은 뜻의 한국어가 영어보다 더 많은 토큰을 사용할 수 있지만, 모든 모델과 문장에 고정 비율을 적용할 수는 없습니다.

숫자, URL, 긴 식별자, 코드, 이모지도 겉보기 길이와 토큰 수가 다를 수 있습니다. 정확한 비교가 필요하면 **실제로 사용할 모델에 맞는 토크나이저나 공식 토큰 계산 기능**으로 측정해야 합니다.

### 이미지·음성의 토큰은 글 조각과 같지 않다

멀티모달 모델에서는 이미지·음성·영상도 모델이 처리할 내부 표현으로 변환됩니다. 서비스가 이를 토큰 수로 보고하더라도 “이미지 한 장이 단어 몇 개로 바뀐다”는 뜻은 아닙니다.

입력 유형, 해상도, 길이와 모델별 처리 방식에 따라 산정이 달라질 수 있습니다. 텍스트용 글자 수 환산법을 그대로 적용하지 말고, [해당 서비스의 멀티모달 토큰 계산 안내](https://ai.google.dev/gemini-api/docs/tokens)를 확인해야 합니다.

## 토큰 수를 확인할 때의 순서

정확한 분할 결과를 확인하지 않고 특정 문장의 토큰 수를 단정하는 것보다 다음 순서로 점검하는 편이 안전합니다.

1. 사용할 모델과 그 모델에 맞는 토크나이저를 확인합니다.
2. 토큰화 결과에서 조각, ID, 개수를 구분해 봅니다.
3. 채팅 요청이라면 메시지 템플릿과 함께 전달할 자료까지 포함합니다.
4. API를 사용한다면 사전 계산 결과와 응답의 실제 사용량 항목을 비교합니다.
5. 차이가 있다면 도구 정의, 멀티모달 입력, 캐시나 추론 토큰 등의 항목을 확인합니다.

단순히 문장 본문만 토큰화한 수치와 완성된 API 요청의 사용량은 다른 범위를 셀 수 있습니다. 모델에게 “방금 답변이 몇 토큰이야?”라고 묻는 것 역시 실제 사용량 측정 기능을 대체하지 못합니다.

## 토큰을 이해하면 AI 사용법이 달라진다

토큰을 줄이는 것 자체가 목적은 아닙니다. 작업에 필요한 정보를 유지하면서 불필요한 반복을 줄이는 것이 중요합니다. 문맥을 지나치게 줄여 AI가 추측할 부분이 많아지면 수정 요청이 늘 수 있습니다.

| 상황 | 토큰의 역할을 고려한 대응 |
|---|---|
| 긴 문서를 분석해야 함 | 관련 절을 골라 제공하고 제목·출처를 유지 |
| 대화가 길어져 조건을 놓침 | 결정 사항과 남은 일을 정리해 새 입력에 포함 |
| 답변이 중간에 잘림 | 출력 한도와 종료 사유를 확인하고 결과를 나누어 요청 |
| 비용이 예상보다 큼 | 반복 전달한 이력·자료와 실제 사용량 항목 점검 |
| 출력이 너무 장황함 | 필요한 항목, 문장 수와 형식을 구체적으로 지정 |
| 정확한 글자 수가 필요함 | 생성 후 별도 프로그램으로 길이 검증 |

예를 들어 문서 검토를 맡길 때는 다음처럼 요청할 수 있습니다.

~~~text
목표: 아래 회의록에서 실행할 일을 추출해줘.

출력 형식:
- 할 일 | 담당자 | 기한 | 근거 문장
- 담당자나 기한이 없으면 '미정'으로 표시
- 같은 할 일은 중복해서 적지 않기
- 회의록 전체를 다시 요약하는 서론은 생략

[회의록 시작]
여기에 회의록을 붙여넣기
[회의록 끝]
~~~

이 요청은 필요한 원문을 유지하면서 결과에 필요 없는 반복을 줄입니다. 반면 공백이나 구두점을 무작정 없애는 방법은 토큰 수를 반드시 줄이지도 않고, 읽기와 해석을 어렵게 만들 수 있습니다.

“출력 최대 500토큰”이라는 설정도 정확히 500글자나 완성된 500토큰 답변을 보장하는 지시가 아닙니다. 생성량의 상한과 사람이 원하는 결과 형식을 구분해서 지정해야 합니다.

토큰을 이해하면 AI가 무엇을 입력으로 받았는지, 어떤 단위로 배우고 답하는지, 한도와 비용이 어디에서 생기는지를 함께 볼 수 있습니다. 실제 사용에서는 **필요한 문맥을 충분히 주고, 원하는 출력 범위를 정하고, 측정 도구로 사용량을 확인하는 것**이 중요합니다.
