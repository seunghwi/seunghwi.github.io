LLM이 파일을 읽고, 데이터베이스를 조회하고, 이슈를 만들고, 사내 시스템을 조작하게 하려면 모델과 외부 시스템을 연결해야 합니다. 서비스마다 서로 다른 API 형식과 인증, 도구 설명을 직접 붙이면 AI 애플리케이션과 연동 대상이 늘어날수록 조합의 수와 유지보수 비용도 커집니다.

**MCP(Model Context Protocol)**는 LLM 애플리케이션이 외부 데이터와 기능을 일관된 방식으로 발견하고 사용할 수 있게 하는 공개 프로토콜입니다. 서버는 자신이 제공하는 도구, 리소스와 프롬프트를 표준 메시지로 공개하고, 호스트는 사용자와 모델을 대신해 필요한 기능을 선택하고 호출합니다.

MCP는 모델도, 에이전트 프레임워크도, 데이터베이스도 아닙니다. 서로 다른 AI 애플리케이션과 외부 시스템 사이에서 **어떤 기능이 있고, 어떤 입력을 받으며, 어떻게 호출하고 결과를 돌려주는지**를 합의하는 연결 규격입니다.

이 글은 **2026년 9월을 기준**으로 [MCP 2026-07-28 사양](https://modelcontextprotocol.io/specification/2026-07-28)과 [공식 Python SDK v2](https://github.com/modelcontextprotocol/python-sdk)를 참고해 작성했습니다. MCP는 빠르게 발전하고 있으며 2026-07-28 사양은 이전 버전의 연결 단위 세션과 `initialize` 중심 구조를 크게 변경했습니다. 오래된 예제와 혼용하지 말고 사용하는 클라이언트·서버·SDK가 지원하는 프로토콜 버전을 확인해야 합니다.
{: .notice--warning}

## 먼저 결론: MCP는 AI 연결을 위한 공통 어댑터다

MCP의 역할을 가장 단순하게 표현하면 다음과 같습니다.

~~~text
MCP가 없을 때

AI 앱 A ── 전용 코드 ── Git 서비스
AI 앱 A ── 전용 코드 ── 사내 DB
AI 앱 B ── 다른 코드 ── Git 서비스
AI 앱 B ── 다른 코드 ── 사내 DB


MCP를 사용할 때

AI 앱 A ─┐                 ┌─ Git MCP 서버 ─ Git 서비스
         ├─ MCP 공통 규격 ─┤
AI 앱 B ─┘                 └─ DB MCP 서버 ─ 사내 DB
~~~

MCP 서버를 한 번 만들었다고 모든 AI 앱에서 자동으로 완벽하게 동작하는 것은 아닙니다. 호스트가 해당 프로토콜 버전과 기능을 지원해야 하고, 인증·권한·사용자 승인·도구 이름 충돌과 모델별 도구 선택 성능도 고려해야 합니다. 그래도 연결 방식을 표준화하면 각 조합마다 별도 플러그인 규격을 만드는 일을 크게 줄일 수 있습니다.

## MCP가 해결하려는 문제

LLM 자체는 텍스트나 멀티모달 입력을 받아 출력을 생성할 뿐입니다. 로컬 파일, 최신 주문 상태, 비공개 문서와 외부 API는 모델의 파라미터 안에 있지 않습니다. 모델에게 이런 기능을 제공하려면 애플리케이션이 다음 일을 해야 합니다.

1. 사용할 수 있는 기능과 데이터를 모델 또는 사용자에게 설명합니다.
2. 입력 형식과 제약을 기계가 이해할 수 있는 스키마로 제공합니다.
3. 모델이 선택한 호출을 실제 시스템에 전달합니다.
4. 실행 결과와 오류를 모델이 다시 사용할 수 있는 형태로 반환합니다.
5. 인증, 권한, 승인, 제한 시간과 감사 기록을 관리합니다.

도구 호출 자체는 MCP 이전에도 가능했습니다. 문제는 모델 제공자와 애플리케이션마다 도구 정의와 연결 방식이 달랐다는 점입니다. MCP는 LSP(Language Server Protocol)가 편집기와 언어 서버의 연결 방식을 표준화한 것처럼, AI 애플리케이션과 컨텍스트 제공자의 통신 방식을 표준화하려고 합니다.

## MCP의 세 구성 요소

[공식 아키텍처 문서](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture)는 MCP를 Host, Client, Server로 나눕니다.

### Host

**호스트(Host)**는 사용자가 직접 이용하는 AI 애플리케이션입니다. 채팅 앱, 코딩 도구, IDE, 데스크톱 앱 또는 에이전트 실행기가 호스트가 될 수 있습니다.

호스트는 다음 책임을 가집니다.

- 모델과 대화 흐름 관리
- 연결할 MCP 서버와 권한 결정
- 서버가 제공한 기능을 모델과 UI에 노출
- 민감한 도구 호출에 대한 사용자 확인
- 여러 서버의 결과와 전체 컨텍스트 조합
- 비밀 정보와 서버 사이의 보안 경계 유지

전체 대화와 모델 선택은 일반적으로 호스트가 관리합니다. MCP 서버가 호스트의 모든 대화나 다른 서버의 정보를 자동으로 볼 수 있는 것은 아닙니다.

### Client

**클라이언트(Client)**는 호스트 안에서 MCP 메시지를 처리하는 구성 요소입니다. 서버의 기능을 발견하고, 요청을 보내고, 응답과 알림을 호스트에 전달합니다.

사용자 관점에서는 별도의 프로그램으로 보이지 않는 경우가 많습니다. 호스트가 여러 MCP 서버에 연결한다면 각 서버와 통신하는 클라이언트 구성 요소가 존재한다고 이해하면 됩니다.

### Server

**서버(Server)**는 외부 시스템의 데이터와 동작을 MCP 형식으로 제공하는 프로그램입니다. 로컬 자식 프로세스일 수도 있고 인터넷에 배포된 원격 서비스일 수도 있습니다.

예를 들면 다음과 같습니다.

- 파일 시스템 서버: 허용된 디렉터리의 파일 읽기와 쓰기
- Git 서버: 커밋 기록 조회와 브랜치 작업
- 데이터베이스 서버: 스키마 확인과 승인된 쿼리 실행
- 업무 시스템 서버: 티켓 검색, 생성과 상태 변경
- 사내 지식 서버: 규정과 문서 검색

서버는 특정 모델에 종속될 필요가 없습니다. 프로토콜을 구현하고 자신의 기능을 정확한 스키마와 설명으로 공개하는 것이 핵심입니다.

## 데이터 계층과 전송 계층

MCP는 크게 두 계층으로 볼 수 있습니다.

| 계층 | 담당하는 것 | 대표 요소 |
|---|---|---|
| 데이터 계층 | 메시지의 의미와 기능 | JSON-RPC, 도구, 리소스, 프롬프트, 오류, 알림 |
| 전송 계층 | 메시지를 실제로 전달하는 방법 | stdio, Streamable HTTP |

같은 `tools/call` 요청도 로컬에서는 표준 입출력을 통해, 원격에서는 HTTP를 통해 전달할 수 있습니다. 전송 방식이 달라져도 도구 호출이라는 의미는 같습니다.

## JSON-RPC 메시지

MCP 데이터 계층은 JSON-RPC 2.0을 기반으로 합니다. 기본 메시지는 요청, 응답과 알림으로 나뉩니다.

- **요청(Request)**: `id`와 `method`가 있으며 상대의 응답을 기다립니다.
- **응답(Response)**: 같은 `id`에 대한 `result` 또는 `error`를 돌려줍니다.
- **알림(Notification)**: `id`가 없으며 응답을 요구하지 않습니다.

예를 들어 클라이언트가 덧셈 도구를 호출하는 메시지의 핵심 부분은 다음과 같습니다. 실제 2026-07-28 요청에는 프로토콜 버전, 클라이언트 정보와 기능을 나타내는 `_meta` 필드도 포함됩니다.

~~~json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "add",
    "arguments": {
      "a": 10,
      "b": 20
    }
  }
}
~~~

응답은 다음과 같은 형태가 됩니다.

~~~json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "resultType": "complete",
    "content": [
      {
        "type": "text",
        "text": "30"
      }
    ],
    "structuredContent": 30,
    "isError": false
  }
}
~~~

SDK는 함수의 타입 힌트와 반환값을 이용해 이런 메시지를 대신 처리하므로 일반적인 서버 개발자가 JSON-RPC를 직접 조립할 필요는 없습니다. 다만 통신 오류를 분석하거나 서로 다른 버전의 구현을 연결할 때 기본 메시지 구조를 알면 도움이 됩니다.

## 발견과 기능 협상

클라이언트는 서버에 무작정 요청을 보내기 전에 서버가 어떤 프로토콜 버전과 기능을 지원하는지 알아야 합니다. 2026-07-28 사양에서는 서버가 필수 `server/discover` 요청으로 지원 버전, 서버 정보와 `tools`, `resources`, `prompts` 같은 capability를 알립니다.

각 요청은 `_meta`에 다음과 같은 정보를 포함합니다.

- 요청이 사용하는 프로토콜 버전
- 클라이언트 이름과 구현 버전
- 클라이언트가 지원하는 기능

이 구조는 요청 하나를 독립적으로 처리할 수 있게 합니다. 서버는 연결에 묶인 암묵적 상태에 의존하지 말아야 하며, 장바구니나 브라우저 작업처럼 여러 호출에 걸쳐 상태가 필요하면 명시적인 `basket_id`, `session_handle` 같은 핸들을 결과로 반환하고 다음 요청에서 다시 받아야 합니다.

2025-11-25 이전 구조를 설명하는 자료에는 연결 직후 `initialize` 요청과 `initialized` 알림을 주고받고 세션 전체에서 기능을 협상하는 과정이 나옵니다. 이는 해당 버전에서는 맞지만 현재 사양과는 다릅니다. 최신 SDK는 이전 사양과의 호환 계층을 제공할 수 있으나 직접 프로토콜을 구현한다면 버전별 규칙을 섞어서는 안 됩니다.
{: .notice--info}

## 서버가 제공하는 세 가지 핵심 Primitive

### Tools: 모델이 실행하는 동작

**도구(Tool)**는 모델이 호출할 수 있는 함수입니다. 데이터 조회, 계산, 파일 변경, 메시지 전송과 배포처럼 읽기와 쓰기 작업을 모두 표현할 수 있습니다.

도구 정의에는 일반적으로 다음 정보가 있습니다.

- 고유한 `name`
- 사람이 읽을 수 있는 `title`과 `description`
- 인자를 정의하는 JSON `inputSchema`
- 선택적인 `outputSchema`
- 읽기 전용 여부나 파괴적 작업 여부를 나타내는 annotation

클라이언트는 `tools/list`로 현재 사용할 수 있는 도구를 발견하고 `tools/call`로 실행합니다. [도구 사양](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)은 입력 스키마에 JSON Schema를 사용하고, 텍스트뿐 아니라 이미지, 오디오, 리소스 링크와 구조화된 JSON 결과도 반환할 수 있도록 정의합니다.

~~~text
사용자: "두 수 10과 20을 더해줘"
  → 호스트가 add 도구 정의를 모델에 제공
  → 모델이 add(a=10, b=20)를 선택
  → 사용자가 필요하면 실행 승인
  → 클라이언트가 tools/call 전송
  → 서버가 30 반환
  → 모델이 결과를 자연어로 설명
~~~

모델이 도구를 선택한다는 것은 실행 권한까지 자동으로 가진다는 뜻이 아닙니다. 결제, 삭제, 외부 전송과 시스템 변경은 사용자가 호출 내용과 영향을 확인할 수 있어야 합니다.

### Resources: 애플리케이션이 가져오는 데이터

**리소스(Resource)**는 모델의 컨텍스트로 사용할 수 있는 데이터입니다. 파일 내용, 데이터베이스 스키마, API 응답, 로그와 문서 등이 될 수 있으며 각 리소스는 URI로 식별됩니다.

~~~text
file:///workspace/README.md
schema://sales/orders
docs://handbook/security-policy
~~~

클라이언트는 `resources/list`로 리소스를 찾고 `resources/read`로 내용을 읽을 수 있습니다. URI에 변수가 있는 **리소스 템플릿**을 사용하면 `customer://{customer_id}/profile`처럼 동적인 대상을 표현할 수 있습니다.

도구와 리소스의 경계는 기술적으로 겹칠 수 있지만 의도는 다릅니다.

- 리소스는 애플리케이션이나 사용자가 **읽어서 컨텍스트에 넣는 데이터**에 가깝습니다.
- 도구는 모델이 목적을 달성하기 위해 **실행하는 동작**에 가깝습니다.

단순 조회라고 모두 리소스일 필요는 없습니다. 검색어나 복잡한 필터가 필요하고 결과가 매번 달라진다면 조회 도구가 더 자연스러울 수 있습니다.

### Prompts: 사용자가 고르는 재사용 템플릿

**프롬프트(Prompt)**는 서버가 제공하는 재사용 가능한 메시지 템플릿입니다. 코드 리뷰, 장애 분석, 보고서 작성처럼 조직이 권장하는 작업 절차와 입력 변수를 묶을 수 있습니다.

클라이언트는 `prompts/list`로 목록을 보고 `prompts/get`으로 인자를 넣어 실제 메시지를 만듭니다. 프롬프트는 모델이 자동 실행하는 함수라기보다 사용자가 명시적으로 선택하는 명령이나 워크플로 템플릿으로 제시되는 경우가 많습니다.

| Primitive | 주된 제어 주체 | 목적 | 예시 |
|---|---|---|---|
| Tool | 모델, 실행은 호스트가 통제 | 외부 동작 수행 | 이슈 생성, DB 조회, 계산 |
| Resource | 애플리케이션 | 컨텍스트 데이터 제공 | 파일, 스키마, 정책 문서 |
| Prompt | 사용자 | 재사용 작업 시작 | 코드 리뷰, 회의록 요약 |

## 클라이언트 기능과 확장

서버가 기능을 제공하기만 하는 단방향 구조로는 복잡한 작업을 모두 표현하기 어렵습니다. 현재 사양은 서버가 작업 도중 사용자에게 추가 정보를 요청하는 **elicitation**을 클라이언트 기능으로 정의합니다.

예를 들어 예약 도구에 날짜가 빠졌다면 단순 실패 대신 날짜 입력 양식을 요청하고, 클라이언트가 사용자 응답을 받아 원래 호출을 이어갈 수 있습니다. 사용자는 입력을 승인하거나 거절하거나 취소할 수 있어야 합니다.

이전 사양의 **sampling**은 MCP 서버가 호스트의 LLM 호출을 요청하는 기능이었지만 2026-07-28 사양에서는 deprecated 상태입니다. 새 구현은 모델 제공자 API를 직접 연결하는 방향을 검토해야 합니다.

핵심 프로토콜 밖에는 선택적으로 합의하는 확장도 있습니다.

- **Tasks**: 오래 걸리는 작업의 비동기 실행, 상태 조회와 결과 회수
- **Skills over MCP**: 에이전트 작업에 필요한 구조화된 지침 제공
- **MCP Apps**: 대화 안에서 차트, 폼 같은 상호작용 UI 제공

확장은 클라이언트와 서버가 모두 명시적으로 지원할 때만 사용할 수 있습니다. 핵심 기능만 필요한 서버에 실험적 확장을 모두 추가할 필요는 없습니다.

## stdio와 Streamable HTTP

[전송 사양](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports)은 두 가지 표준 전송 방식을 정의합니다.

### stdio

호스트가 MCP 서버를 자식 프로세스로 실행하고 표준 입력과 표준 출력으로 줄 단위 JSON-RPC 메시지를 주고받습니다.

- 개인 PC의 로컬 도구에 적합합니다.
- 별도 포트나 웹 서버가 필요 없습니다.
- 프로세스 실행 권한과 로컬 파일 접근 범위를 신중히 제한해야 합니다.
- `stdout`은 프로토콜 전용이므로 일반 로그를 출력하면 메시지가 깨질 수 있습니다.
- 로그는 `stderr` 또는 별도 파일로 보냅니다.

### Streamable HTTP

각 메시지를 하나의 MCP HTTP endpoint에 `POST`하고, 응답은 JSON 객체 또는 요청 범위의 SSE 스트림으로 받습니다.

- 원격 서비스와 여러 사용자가 공유하는 서버에 적합합니다.
- HTTPS, 인증, 접근 제어, rate limit과 관측성이 필요합니다.
- 프록시와 로드 밸런서의 timeout, 스트리밍과 요청 크기 설정을 확인해야 합니다.
- 서버 주소만 안다고 접근할 수 없도록 사용자와 서비스 권한을 검증해야 합니다.

예전 문서의 독립적인 SSE transport는 최신 구현의 출발점으로 삼지 않는 편이 좋습니다. Streamable HTTP 안에서 필요한 응답 스트리밍에 SSE가 사용될 수 있다는 것과 구형 SSE transport는 구분해야 합니다.

## Function calling, API, RAG와 무엇이 다른가

### MCP와 Function calling

Function calling 또는 tool calling은 모델에게 함수 스키마를 주고 호출할 함수와 인자를 생성하게 하는 **모델 API 기능**입니다. MCP는 서버에서 도구를 발견하고 호출하고 결과를 전달하는 **애플리케이션 통신 규격**입니다.

호스트는 MCP의 `tools/list` 결과를 모델 제공자의 function calling 형식으로 변환하고, 모델이 선택한 호출을 MCP `tools/call`로 보낼 수 있습니다. 둘은 경쟁 기술이 아니라 서로 다른 계층입니다.

### MCP와 REST·GraphQL API

REST와 GraphQL은 일반 애플리케이션이 서비스를 호출하는 API 설계 방식입니다. MCP 서버는 내부에서 기존 REST API나 데이터베이스를 호출하는 어댑터 역할을 할 수 있습니다.

MCP가 기존 API를 없애는 것은 아닙니다. AI 호스트가 기능을 발견하고 모델 친화적인 스키마로 사용할 수 있도록 공통 표면을 추가합니다. 일반 웹·모바일 클라이언트까지 MCP로 바꿀 이유는 없습니다.

### MCP와 RAG

RAG는 질문과 관련된 외부 지식을 검색해 모델 컨텍스트에 넣는 **AI 시스템 설계 방식**입니다. MCP는 검색기, 문서 리소스 또는 데이터 도구를 호스트에 연결하는 방법이 될 수 있습니다.

MCP 서버를 연결했다고 자동으로 RAG 품질이 좋아지는 것은 아닙니다. 문서 정제, 청킹, 검색, reranking, 권한 필터와 근거 검증은 여전히 별도로 설계해야 합니다.

### MCP와 에이전트

에이전트는 목표를 달성하기 위해 모델과 도구를 반복 실행하고 상태와 흐름을 관리하는 시스템입니다. MCP는 에이전트가 사용할 도구와 컨텍스트를 제공할 수 있지만 계획, 반복, 실패 복구와 메모리를 대신 구현하지 않습니다.

## 간단한 Python MCP 서버 만들기

다음 예제는 공식 Python SDK v2의 `MCPServer`를 사용합니다. 두 수를 더하는 도구, 이름별 인사말 리소스와 코드 리뷰 프롬프트를 제공합니다.

### 1. 프로젝트와 SDK 준비

Python 3.10 이상과 `uv`가 준비되어 있다고 가정합니다.

~~~bash
uv init mcp-demo
cd mcp-demo
uv add "mcp[cli]"
~~~

SDK의 major version에 따라 import와 실행 API가 다를 수 있습니다. 이 예제는 Python SDK 2.x 기준입니다.
{: .notice--info}

### 2. 서버 코드 작성

`server.py`를 만들고 다음 코드를 작성합니다.

~~~python
from mcp.server import MCPServer


mcp = MCPServer("blog-demo")


@mcp.tool()
def add(a: int, b: int) -> int:
    """두 정수를 더합니다."""
    return a + b


@mcp.resource("greeting://{name}")
def greeting(name: str) -> str:
    """이름을 받아 인사말을 반환합니다."""
    return f"안녕하세요, {name}님!"


@mcp.prompt()
def review_code(code: str) -> str:
    """안전성과 가독성 중심의 코드 리뷰 요청을 만듭니다."""
    return (
        "다음 코드를 안전성, 오류 가능성, 가독성 순서로 검토하세요.\n\n"
        f"{code}"
    )


if __name__ == "__main__":
    mcp.run(transport="stdio")
~~~

`@mcp.tool()`은 함수 이름, docstring과 타입 힌트에서 도구 설명과 입력 스키마를 만듭니다. `@mcp.resource()`의 URI에 `{name}`이 있으므로 이것은 고정 리소스가 아니라 인자를 받는 리소스 템플릿입니다. `@mcp.prompt()`는 입력을 받아 재사용 가능한 메시지를 만듭니다.

### 3. Inspector에서 확인

공식 MCP Inspector로 서버를 실행합니다.

~~~bash
uv run mcp dev server.py
~~~

출력된 주소를 브라우저에서 열면 도구, 리소스 템플릿과 프롬프트를 각각 확인할 수 있습니다.

- `add`에 `a=10`, `b=20`을 넣으면 `30`을 반환합니다.
- `greeting://{name}`에 `name=SH`를 넣으면 인사말을 읽습니다.
- `review_code`에 코드를 넣으면 모델에 전달할 리뷰 메시지를 만듭니다.

Inspector는 개발과 디버깅 도구입니다. 프로덕션 서버의 인증과 권한 검사를 대신하지 않습니다.

### 4. 일반적인 stdio 호스트 설정 형태

stdio 서버를 지원하는 호스트는 대체로 실행 명령과 인자, 작업 디렉터리 또는 환경 변수를 설정합니다. 제품마다 설정 키와 파일 위치는 다르지만 개념적인 형태는 다음과 같습니다.

~~~json
{
  "mcpServers": {
    "blog-demo": {
      "command": "uv",
      "args": [
        "--directory",
        "/absolute/path/to/mcp-demo",
        "run",
        "server.py"
      ]
    }
  }
}
~~~

상대 경로보다 명확한 절대 경로를 사용하고, 호스트가 실행되는 환경에서 `uv`를 찾을 수 있는지 확인합니다. API 키는 코드나 블로그에 넣지 말고 호스트의 비밀 관리 또는 환경 변수 기능을 사용합니다.

## 좋은 MCP 도구를 설계하는 방법

### 하나의 분명한 작업을 표현한다

`manage_everything`처럼 수많은 동작을 문자열 인자 하나로 받는 도구보다 `search_issues`, `create_issue`, `close_issue`처럼 목적과 권한이 분명한 도구가 모델과 사용자 모두에게 이해하기 쉽습니다.

도구를 너무 잘게 나누면 모델이 긴 절차를 매번 조립해야 하고 목록도 커집니다. 업무적으로 하나의 원자적 작업이 무엇인지 기준을 세워 적절한 단위를 찾습니다.

### 이름과 설명을 실행 계약으로 생각한다

모델은 이름, 설명과 스키마를 보고 도구를 선택합니다. 설명에는 다음을 명확히 적습니다.

- 도구가 하는 일과 하지 않는 일
- 언제 사용해야 하는지
- 읽기인지 변경 작업인지
- 인자의 단위, 형식과 허용 범위
- 결과와 대표적인 오류

`run`, `do_task` 같은 모호한 이름은 피하고 서버 안에서 이름을 고유하게 유지합니다. 여러 서버를 합치는 호스트에서는 같은 `search` 이름이 충돌할 수 있으므로 서버 식별자를 붙이는 전략도 필요합니다.

### 입력과 출력을 구조화한다

자유로운 문자열 하나보다 enum, required, 최소·최대 길이와 형식을 포함한 JSON Schema가 안전합니다. 반환값에도 `outputSchema`와 `structuredContent`를 사용하면 클라이언트가 결과를 검증하고 모델이 필드를 안정적으로 사용할 수 있습니다.

하지만 스키마 검증은 업무 권한 검사가 아닙니다. `issue_id`가 문자열 형식에 맞더라도 사용자가 그 이슈를 읽거나 수정할 권한이 있는지 서버에서 별도로 확인해야 합니다.

### 읽기와 쓰기를 구분하고 멱등성을 고려한다

네트워크 timeout 뒤에 클라이언트가 같은 요청을 재시도하면 결제가 두 번 처리되거나 티켓이 중복 생성될 수 있습니다. 변경 도구에는 idempotency key, 중복 검사 또는 명시적인 작업 ID를 적용합니다.

조회와 변경을 하나의 도구에 섞지 않으면 사용자 승인과 감사 정책을 적용하기 쉽습니다. 삭제처럼 복구하기 어려운 작업은 대상과 영향 범위를 반환하는 미리보기 도구를 제공할 수도 있습니다.

### 오류를 모델이 고칠 수 있게 반환한다

`failed`만 반환하지 말고 어떤 인자가 왜 잘못됐는지, 재시도 가능한지와 사용자가 무엇을 해야 하는지 알려줍니다. 모델이 수정할 수 있는 입력 오류는 도구 실행 결과의 오류로 전달하고, 잘못된 JSON-RPC나 존재하지 않는 method 같은 프로토콜 오류와 구분합니다.

### timeout, 취소와 긴 작업을 설계한다

모든 호출에 제한 시간을 두고, 클라이언트의 취소 신호를 실제 하위 API와 작업에 전달합니다. 오래 걸리는 배치 작업은 연결을 계속 붙잡기보다 비동기 작업 ID를 반환하고 Tasks 확장이나 별도 상태 조회 도구를 사용하는 방법을 검토합니다.

## 보안에서 반드시 확인할 것

MCP 서버는 모델이 외부 시스템에 접근하는 경로이므로 일반 플러그인보다 좁게 권한을 부여해야 합니다. [MCP 보안 권고](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices)는 token passthrough, confused deputy, SSRF, 세션 탈취와 로컬 서버 침해 같은 위험을 다룹니다.

### 최소 권한

- 읽기만 필요한 서버에 쓰기 권한을 주지 않습니다.
- 파일 서버는 허용된 디렉터리 밖으로 나가지 못하게 합니다.
- 데이터베이스 계정은 필요한 table과 query만 허용합니다.
- 사용자별 권한을 서버에서 다시 검증합니다.
- 도구 목록도 현재 권한으로 사용할 수 있는 기능만 반환합니다.

### 사용자 승인과 투명성

호스트는 어떤 서버와 도구가 모델에 노출됐는지 보여줘야 합니다. 삭제, 결제, 게시, 메시지 전송과 개인정보 접근 전에는 대상과 인자를 확인할 수 있어야 합니다. “모델이 선택했다”는 것은 사용자 동의가 아닙니다.

### 입력·출력 검증

모델이 만든 인자를 신뢰하지 말고 schema와 업무 규칙을 모두 검증합니다. 파일 경로 traversal, SQL injection, shell command injection과 URL 기반 SSRF를 막아야 합니다. 서버 결과도 프롬프트 인젝션이나 민감 정보가 포함될 수 있으므로 호스트에서 신뢰 수준을 구분합니다.

### 인증 토큰

원격 HTTP 서버는 HTTPS와 표준 인증 흐름을 사용합니다. 다른 서비스용 access token을 검증 없이 받아 그대로 하위 API에 전달하는 token passthrough는 피해야 합니다. 토큰의 발급 대상, scope, 만료와 사용자를 검증하고 로그에 토큰을 남기지 않습니다.

stdio에서는 OAuth 흐름보다 호스트가 서버 프로세스에 필요한 자격 증명을 환경 변수나 안전한 비밀 저장소로 전달하는 방식이 일반적입니다. 설정 파일에 평문 비밀을 넣어 저장소에 커밋하지 않습니다.

### 신뢰할 수 있는 서버만 설치한다

로컬 MCP 서버는 사용자의 권한으로 실행되는 프로그램입니다. 서버 패키지를 설치한다는 것은 일반 프로그램을 설치하는 것과 같은 위험을 가집니다. 이름이 비슷한 패키지를 피하고 공식 배포처, 소스, 버전 고정, 의존성과 실행 명령을 확인합니다.

MCP라는 표준을 사용한다는 사실 자체가 서버를 안전하게 만들지는 않습니다. 프로토콜은 통신 규격을 제공하지만 서버 코드, 권한과 사용자의 승인 정책까지 자동으로 검증하지 않습니다.
{: .notice--danger}

## 자주 생기는 오해와 문제

### MCP 서버 안에 LLM이 반드시 필요한가

아닙니다. 대부분의 서버는 API, 데이터베이스 또는 로컬 기능을 MCP로 감싸는 일반 프로그램입니다. 모델 호출과 대화는 호스트가 담당할 수 있습니다.

### 서버를 많이 연결할수록 좋은가

도구 목록이 지나치게 길거나 설명이 비슷하면 모델의 선택이 어려워지고 입력 토큰과 지연 시간이 늘 수 있습니다. 사용자와 작업에 필요한 서버만 활성화하고, 권한에 따라 도구를 필터링하며 실제 호출 성공률을 측정해야 합니다.

### MCP가 정확성을 보장하는가

MCP는 도구의 실제 내용과 결과가 옳은지 보장하지 않습니다. 모델이 잘못된 도구나 인자를 선택할 수도 있고 서버가 잘못된 값을 반환할 수도 있습니다. 입력 검증, 결과 검증, 업무 규칙과 평가셋이 여전히 필요합니다.

### stdio 서버가 실행되지만 연결되지 않는다

stdio의 `stdout`에 시작 메시지나 debug 로그를 출력하면 JSON-RPC 스트림이 손상될 수 있습니다. 로그를 `stderr`로 보내고, 실행 명령의 절대 경로와 작업 디렉터리, Python 환경, 패키지 버전과 환경 변수를 확인합니다.

### 예제의 API가 내 환경과 다르다

MCP 사양 버전과 언어 SDK 버전은 별개입니다. 예를 들어 Python SDK v1과 v2는 import와 클래스 이름이 다릅니다. 블로그 예제를 복사하기 전에 SDK의 major version과 해당 버전 문서를 확인합니다.

## 어디에 적용할 수 있는가

| 영역 | MCP 서버가 제공할 수 있는 기능 |
|---|---|
| 개발 도구 | 저장소 탐색, 테스트 실행, 이슈·배포 상태 조회 |
| 데이터 분석 | 스키마 제공, 승인된 쿼리 실행, 차트 데이터 반환 |
| 사내 업무 | 문서 검색, 티켓 생성, 결재·일정 시스템 연동 |
| 고객 지원 | 주문 조회, 환불 조건 확인, 상담 이력 검색 |
| 인프라 운영 | 로그와 지표 조회, runbook 제공, 승인된 운영 작업 |
| 개인 생산성 | 파일, 메모, 캘린더와 할 일 관리 |

읽기 전용 검색부터 시작해 관측성과 평가를 확보한 뒤, 쓰기 작업은 권한과 사용자 승인 단계를 추가하며 점진적으로 넓히는 편이 안전합니다.

## 도입 순서

1. 해결하려는 사용자 작업과 필요한 외부 시스템을 정의합니다.
2. 기존 API와 권한 모델을 먼저 정리합니다.
3. 읽기 전용이며 영향이 작은 도구 한두 개로 시작합니다.
4. 명확한 이름, 설명, 입력·출력 schema를 작성합니다.
5. Inspector와 자동 테스트로 정상 결과, 오류와 경계값을 확인합니다.
6. 실제 호스트에서 도구 선택률과 인자 정확도를 평가합니다.
7. 인증, 최소 권한, timeout, rate limit과 감사 로그를 적용합니다.
8. 쓰기 작업에는 사용자 승인과 중복 실행 방지를 추가합니다.
9. 프로토콜과 SDK 버전을 고정하고 업그레이드 시 호환성을 다시 시험합니다.

## 정리

MCP는 AI 애플리케이션과 외부 세계를 연결하는 공통 언어입니다.

- Host는 사용자 경험, 모델, 권한과 전체 흐름을 관리합니다.
- Client는 호스트 안에서 MCP 서버와 통신합니다.
- Server는 도구, 리소스와 프롬프트를 제공합니다.
- JSON-RPC 데이터 계층은 메시지 의미를, stdio와 Streamable HTTP는 전달 방식을 정의합니다.
- Function calling, REST API, RAG와 에이전트를 대체하지 않고 이들을 연결하는 계층으로 사용할 수 있습니다.
- 표준 연결은 편의성을 높이지만 보안, 정확성, 사용자 승인과 운영 책임을 없애지 않습니다.

좋은 MCP 서버는 기능이 많은 서버가 아니라 경계가 명확하고, 최소 권한으로 동작하며, 모델과 사용자가 결과를 예측할 수 있는 서버입니다. 작고 읽기 전용인 연동부터 시작해 평가와 통제를 갖춘 뒤 필요한 기능만 확장하는 것이 현실적인 접근입니다.
