상품 검색에서 “출근할 때 신기 좋은 편안한 신발”과 의미가 가까운 상품을 찾고 싶다면 **벡터 데이터베이스(Vector Database)**가 유용합니다. 반면 “이 계정과 같은 전화번호·기기·결제 수단을 공유하는 의심 계정을 찾아라”처럼 여러 연결을 따라가야 한다면 **그래프 데이터베이스(Graph Database)**가 잘 맞습니다.

두 데이터베이스는 모두 전통적인 행과 열만으로 표현하기 까다로운 문제를 다루지만, 질문의 방향이 다릅니다.

~~~text
벡터 DB:  이 데이터와 의미·특징이 가장 비슷한 것은 무엇인가?
그래프 DB: 이 개체는 무엇과 어떻게 연결돼 있으며, 어떤 경로가 존재하는가?
~~~

이 글에서는 벡터 DB와 그래프 DB의 데이터 모델, 검색 방식과 장단점을 살펴보고 어떤 상황에서 각각 유용한지 정리합니다.

## 먼저 비교하기

| 구분 | 벡터 DB | 그래프 DB |
|---|---|---|
| 중심 데이터 | 고차원 숫자 벡터와 메타데이터 | 노드, 관계와 속성 |
| 대표 질문 | 가장 가까운 항목은 무엇인가 | 어떤 경로로 연결돼 있는가 |
| 주요 연산 | nearest neighbor, 유사도·거리 계산 | 관계 순회, 경로·패턴 탐색 |
| 결과 근거 | 벡터 공간에서의 가까움 | 명시적으로 저장된 관계와 경로 |
| 대표 활용 | 의미 검색, RAG, 이미지 검색, 유사 상품 | 사기 탐지, 지식 그래프, 권한, 네트워크 분석 |
| 설계 핵심 | 임베딩 모델, 거리 함수, 검색 품질 | 노드·관계 모델과 탐색 패턴 |
| 주의할 점 | 의미적 유사성이 사실이나 동일성을 보장하지 않음 | 좋은 결과를 위해 관계 데이터를 명시적으로 구축해야 함 |

벡터 DB와 그래프 DB는 제품 이름이 아니라 데이터 모델과 질의 방식에 가까운 분류입니다. 한 제품이 관계형 데이터, 벡터 인덱스와 그래프 기능을 함께 제공할 수도 있습니다.

## 벡터 데이터베이스란

벡터 DB는 텍스트, 이미지, 음성, 상품이나 사용자 행동을 **임베딩(embedding)**이라는 숫자 배열로 저장하고, 주어진 질의 벡터와 가까운 항목을 빠르게 찾도록 설계된 데이터베이스입니다.

예를 들어 임베딩 모델이 다음 두 문장을 비슷한 벡터로 표현했다고 가정할 수 있습니다.

~~~text
"로그인 비밀번호를 바꾸고 싶어요"
"계정 암호 변경 방법"
~~~

문장에 같은 단어가 거의 없어도 의미가 비슷하면 벡터 공간에서 가까워질 수 있습니다. 벡터 DB는 이 거리를 계산해 관련 문서 후보를 반환합니다.

벡터 DB가 원문을 스스로 이해해 벡터로 바꾸는 것은 아닙니다. 일반적으로 애플리케이션이 임베딩 모델을 호출해 벡터를 만든 뒤 원문, ID와 필터용 메타데이터를 함께 저장합니다.
{: .notice--info}

### 벡터와 임베딩

벡터는 다음과 같은 숫자 배열입니다.

~~~text
[0.021, -0.318, 0.744, ..., 0.105]
~~~

각 숫자를 사람이 직접 해석하기는 어렵지만, 임베딩 모델은 학습 과정에서 텍스트의 의미나 이미지의 시각적 특징이 거리로 비교되도록 표현을 만듭니다. 모델에 따라 벡터 차원과 공간의 성질이 다르므로 서로 다른 임베딩 모델이 만든 벡터를 그대로 비교해서는 안 됩니다.

임베딩 모델을 교체하거나 출력 차원이 바뀌면 기존 데이터도 새 모델로 다시 임베딩해야 하는 경우가 많습니다. 운영 환경에서는 모델 이름, 버전과 전처리 방법을 벡터 데이터와 함께 추적하는 편이 안전합니다.

### 유사도와 거리

벡터 검색은 질의 벡터와 저장된 벡터 사이의 가까움을 계산합니다. 흔히 사용하는 기준은 다음과 같습니다.

- **Cosine similarity 또는 cosine distance**: 벡터 방향이 얼마나 비슷한지 비교
- **Inner product**: 두 벡터의 내적을 비교
- **Euclidean distance·L2 distance**: 공간에서 두 점 사이의 직선거리를 비교

어떤 기준이 좋은지는 임베딩 모델이 권장하는 방식과 벡터 정규화 여부에 따라 달라집니다. 같은 데이터라도 거리 함수를 임의로 바꾸면 검색 순위가 달라질 수 있습니다.

### 정확 검색과 근사 최근접 이웃 검색

모든 벡터와 거리를 계산하면 정확한 결과를 얻을 수 있지만 데이터가 커질수록 비용이 증가합니다. 대규모 시스템은 보통 **ANN(Approximate Nearest Neighbor)** 인덱스를 사용해 일부 후보를 효율적으로 탐색합니다.

ANN은 속도와 메모리를 아끼는 대신 실제 최근접 항목 일부를 놓칠 수 있습니다. 이때 원하는 정답 중 검색 결과가 얼마나 포함됐는지를 **recall**로 측정합니다. 인덱스와 검색 파라미터는 속도, 메모리와 recall 사이의 균형을 결정합니다.

[pgvector 공식 문서](https://github.com/pgvector/pgvector)는 정확 검색과 근사 검색을 모두 지원하며, 근사 인덱스로 HNSW와 IVFFlat을 제공합니다. 문서도 근사 인덱스가 일부 recall을 속도와 교환한다는 점을 명시합니다.

HNSW가 내부적으로 그래프 구조의 인덱스를 사용한다고 해서 벡터 DB가 이 글에서 말하는 그래프 DB가 되는 것은 아닙니다. HNSW의 그래프는 가까운 벡터를 빨리 찾기 위한 인덱스이고, 그래프 DB의 관계는 `구매했다`, `소속된다`처럼 도메인 의미를 가진 데이터입니다.
{: .notice--warning}

### 메타데이터 필터

실제 검색에서는 벡터 거리만으로 결과를 정하지 않습니다. 다음과 같은 구조화된 조건을 함께 적용합니다.

~~~text
의미가 비슷한 문서
+ tenant_id가 현재 고객과 같음
+ language가 ko임
+ 공개 가능한 문서임
+ 유효 기간이 지나지 않음
~~~

필터는 보안에도 중요합니다. 검색한 뒤 애플리케이션 화면에서 숨기는 방식이 아니라, 권한 없는 데이터가 검색 후보와 모델 입력에 들어가지 않도록 질의 단계에서 제한해야 합니다.

### 간단한 벡터 검색 예제

PostgreSQL에 pgvector 확장을 사용한 개념 예제입니다. 실제 임베딩은 보통 세 차원보다 훨씬 크지만 이해를 위해 `vector(3)`을 사용합니다.

~~~sql
CREATE EXTENSION vector;

CREATE TABLE documents (
  id bigserial PRIMARY KEY,
  tenant_id bigint NOT NULL,
  title text NOT NULL,
  content text NOT NULL,
  embedding vector(3) NOT NULL
);

INSERT INTO documents (tenant_id, title, content, embedding)
VALUES
  (42, '비밀번호 변경', '계정 설정에서 암호를 변경합니다.', '[0.10, 0.72, -0.31]'),
  (42, '배송지 변경', '주문 전에 배송 주소를 수정합니다.', '[0.81, -0.12, 0.20]');

SELECT id, title, content
FROM documents
WHERE tenant_id = 42
ORDER BY embedding <=> '[0.08, 0.70, -0.29]'
LIMIT 5;
~~~

pgvector의 `<=>` 연산자는 cosine distance를 뜻합니다. 실제 시스템에서는 질의 문장도 저장할 때와 같은 임베딩 모델과 전처리 과정으로 벡터화해야 합니다.

## 벡터 DB가 유용한 상황

### 의미 기반 문서 검색

사용자가 문서에 쓰인 정확한 단어를 몰라도 의도가 비슷한 내용을 찾을 수 있습니다. 고객 지원 문서, 사내 위키와 논문 검색처럼 표현이 다양한 환경에 유용합니다.

다만 제품 코드, 오류 번호, 고유명사처럼 정확한 문자열이 중요한 질의는 키워드 검색이 더 강할 수 있습니다. 실무에서는 키워드 검색과 벡터 검색 결과를 합치는 **하이브리드 검색**을 자주 검토합니다.

### RAG의 문서 검색

질문과 관련된 문서 청크를 찾고 그 내용을 LLM에 제공하는 RAG에서 벡터 검색을 사용할 수 있습니다. 하지만 벡터 DB만 설치한다고 좋은 RAG가 완성되는 것은 아닙니다. 문서 분할, 메타데이터, 권한 필터, reranking과 답변 출처 검증이 함께 필요합니다.

RAG의 전체 흐름은 [RAG와 Fine-tuning 개념 정리](/topics/ai/rag-and-fine-tuning/)에서 더 자세히 다룹니다.

### 이미지·음성·상품 유사 검색

같은 임베딩 공간으로 표현할 수 있다면 텍스트뿐 아니라 이미지, 음성과 상품도 유사도를 비교할 수 있습니다.

- 업로드한 사진과 비슷한 상품 찾기
- 중복되거나 거의 같은 이미지 탐지
- 음성 구간 또는 음악의 유사 패턴 검색
- 사용자가 본 상품과 특징이 가까운 상품 추천

### 이상 탐지와 군집 후보 생성

정상 데이터 군집에서 멀리 떨어진 벡터를 이상 후보로 표시하거나, 가까운 항목을 묶어 검토 대상을 줄일 수 있습니다. 다만 벡터 거리가 멀다는 사실만으로 부정 행위나 장애라고 단정하지 말고 도메인 규칙과 추가 검증을 결합해야 합니다.

## 벡터 DB가 맞지 않을 수 있는 상황

- ID, 날짜와 금액의 정확한 일치·범위 검색이 대부분인 경우
- 데이터 규모가 작아 일반 DB의 정확 검색으로도 충분한 경우
- 결과가 왜 선택됐는지 명확한 관계 경로로 설명해야 하는 경우
- 여러 단계의 소유·의존·친구 관계를 따라가야 하는 경우
- 임베딩을 안정적으로 만들거나 평가할 데이터가 없는 경우

벡터 검색이 필요하다고 처음부터 별도 전용 시스템을 도입할 필요는 없습니다. 기존 PostgreSQL 같은 데이터베이스의 벡터 확장으로 요구 성능과 운영 복잡도를 먼저 검증하는 방법도 있습니다.

## 그래프 데이터베이스란

그래프 DB는 데이터를 **노드(Node)**, **관계(Relationship 또는 Edge)**와 **속성(Property)**으로 저장하고 연결 패턴과 경로를 효율적으로 질의하도록 설계된 데이터베이스입니다.

~~~text
(사용자:민지)-[:구매함 {날짜: 2026-08-20}]->(상품:카메라)
(사용자:민지)-[:사용함]->(기기:A17)
(사용자:준호)-[:사용함]->(기기:A17)
~~~

- **노드**는 사용자, 상품, 계정과 서버 같은 개체를 나타냅니다.
- **관계**는 구매, 소유, 접속과 의존처럼 두 개체의 연결을 나타냅니다.
- **속성**은 이름, 시간, 금액처럼 노드와 관계의 상세 값을 저장합니다.

[Neo4j의 그래프 DB 개념 문서](https://neo4j.com/docs/getting-started/graph-database/)도 property graph를 노드, 방향과 유형을 가진 관계, 키-값 속성으로 설명합니다.

### 관계가 일급 데이터다

관계형 데이터베이스에서도 외래 키와 JOIN으로 관계를 표현할 수 있습니다. 그래프 DB의 특징은 관계를 단순한 보조 값이 아니라 직접 저장하고 탐색하는 핵심 요소로 다룬다는 점입니다.

질문이 “사용자 한 명의 주문 목록” 정도라면 관계형 DB의 JOIN이 충분할 수 있습니다. 하지만 친구의 친구, 여러 계정이 공유하는 기기, 서비스 간 연쇄 의존성처럼 가변 길이의 연결을 반복 탐색하면 그래프 모델이 문제를 더 자연스럽게 표현할 수 있습니다.

### 경로와 패턴 탐색

그래프 질의는 한 개체에서 시작해 특정 관계를 따라가거나 원하는 모양의 패턴을 찾습니다.

~~~text
계정 ─사용함→ 기기 ←사용함─ 다른 계정 ─결제함→ 카드
~~~

이 패턴을 사용하면 같은 기기와 카드를 공유하는 계정 집단을 찾을 수 있습니다. 관계 방향, 종류, 횟수와 속성을 조건으로 넣어 탐색 범위를 제한할 수 있습니다.

### 간단한 그래프 질의 예제

다음은 Cypher로 사용자가 구매한 상품을 함께 산 다른 사용자가 구매했지만, 원래 사용자는 아직 구매하지 않은 상품을 찾는 개념 예제입니다.

~~~cypher
MATCH (user:User {id: 42})-[:BOUGHT]->(owned:Product)
MATCH (owned)<-[:BOUGHT]-(peer:User)-[:BOUGHT]->(candidate:Product)
WHERE NOT (user)-[:BOUGHT]->(candidate)
RETURN candidate.id, candidate.name, count(DISTINCT peer) AS peerCount
ORDER BY peerCount DESC
LIMIT 10
~~~

괄호는 노드, 대괄호와 화살표는 관계를 표현합니다. 이 추천이 선택된 이유를 “같은 상품을 구매한 사용자들이 함께 구매했다”는 실제 경로로 설명할 수 있습니다.

## 그래프 DB가 유용한 상황

### 사기 조직과 이상 연결 탐지

계정, 이메일, 전화번호, 주소, 기기와 결제 수단을 노드로 만들면 직접 관계뿐 아니라 몇 단계를 거친 공유 관계도 찾을 수 있습니다. 알려진 부정 계정과 연결된 새 계정이나 여러 계정이 반복해서 공유하는 자원을 탐색하는 데 적합합니다.

[Amazon Neptune 공식 시작 문서](https://docs.aws.amazon.com/neptune/latest/userguide/graph-get-started.html)는 그래프 DB의 대표 활용으로 지식 그래프, identity graph와 사기 그래프를 소개합니다.

### 지식 그래프

사람, 조직, 제품, 문서와 개념의 관계를 명시적으로 저장하면 “이 부품을 사용하는 제품의 담당 조직과 관련 장애 문서는 무엇인가” 같은 다단계 질문을 처리할 수 있습니다. 데이터 출처와 관계 유형을 보존하면 결과가 만들어진 경로를 추적하기도 쉽습니다.

### 추천 시스템

사용자-상품-카테고리-브랜드 관계를 따라가며 이웃 사용자나 연관 상품을 찾을 수 있습니다. 벡터 추천이 취향의 유사성을 잘 찾는다면 그래프 추천은 함께 구매함, 팔로우함과 소속됨 같은 실제 행동 관계를 활용하는 데 강점이 있습니다.

### 권한과 조직 구조

사용자, 그룹, 역할, 자원과 상속 관계를 그래프로 나타내면 여러 그룹을 거쳐 전달되는 권한이나 접근 경로를 질의할 수 있습니다. 다만 권한 시스템은 정확성과 보안이 중요하므로 순환 관계, 거부 규칙, 캐시 무효화와 감사 로그까지 명확히 설계해야 합니다.

### 네트워크와 의존성 분석

서버, 애플리케이션, 라이브러리와 네트워크 장비의 의존 관계를 저장하면 한 구성 요소의 장애가 어디까지 영향을 미치는지 추적할 수 있습니다. 공급망, 물류 경로, 통신망과 소프트웨어 dependency 분석에도 같은 구조를 적용할 수 있습니다.

## 그래프 DB가 맞지 않을 수 있는 상황

- 단순 CRUD와 집계가 대부분이고 연결 탐색이 적은 경우
- 테이블 구조와 SQL 분석 도구만으로 요구사항을 충분히 해결하는 경우
- 관계 데이터의 정확한 출처와 갱신 방법을 마련하지 못한 경우
- 대규모 전체 테이블 집계가 핵심이고 그래프 경로 질의가 거의 없는 경우
- 팀이 새로운 데이터 모델과 질의 언어를 운영할 비용이 더 큰 경우

그래프 DB를 도입한다고 숨어 있던 관계가 자동으로 생성되는 것은 아닙니다. 어떤 개체와 관계를 저장할지, 관계의 방향과 의미를 어떻게 유지할지가 검색 성능만큼 중요합니다.

## 가장 중요한 차이: 유사성과 관계

온라인 서점에서 “분산 시스템을 처음 배우기 좋은 책”을 찾는다고 가정해 보겠습니다.

벡터 DB는 질문과 책 소개의 의미를 비교해 입문 난이도와 주제가 비슷한 책을 찾을 수 있습니다. 그래프 DB는 사용자가 읽은 책, 저자, 분야, 다른 독자의 구매 관계를 따라가 후보를 만들 수 있습니다.

~~~text
벡터 검색 결과
질문 ── 의미가 가까움 ──> 책 소개

그래프 검색 결과
나 ─읽음→ 책A ←읽음─ 비슷한 독자 ─읽음→ 책B
~~~

벡터의 가까움은 학습된 표현에 따른 **유사성**이고, 그래프의 연결은 시스템이 저장한 **명시적 사실 또는 이벤트**입니다. 유사도 점수가 높다고 두 항목 사이에 실제 관계가 있다는 뜻은 아니며, 그래프에 경로가 있다고 의미가 비슷하다는 뜻도 아닙니다.

## 둘을 함께 사용하면 좋은 상황

현실의 서비스는 유사성과 관계를 동시에 요구할 수 있습니다.

### 지식 그래프를 활용한 RAG

1. 질문 임베딩으로 관련 문서나 개체 후보를 찾습니다.
2. 그래프에서 후보와 연결된 제품, 조직과 정책을 탐색합니다.
3. 권한과 유효 기간으로 결과를 제한합니다.
4. 선택한 근거와 출처를 LLM 컨텍스트에 제공합니다.

이 방식은 자연어 표현이 다양한 질문을 벡터 검색으로 받아들이면서도, 그래프의 명시적 관계로 관련 범위를 확장하거나 제한할 수 있습니다.

### 추천 결과의 후보 생성과 설명

벡터 검색으로 취향이 비슷한 상품 후보를 넓게 찾고, 그래프에서 재고, 브랜드 관계, 친구의 구매와 사용자가 이미 가진 상품을 반영할 수 있습니다. 반대로 그래프로 후보를 만든 뒤 벡터 유사도로 최종 순위를 정할 수도 있습니다.

### 사기 탐지의 신호 결합

행동 벡터가 평소 패턴과 다른 거래를 후보로 만들고, 그래프 탐색으로 해당 계정이 알려진 위험 기기나 결제 수단과 연결되는지 확인할 수 있습니다. 최종 판정은 규칙, 모델과 사람의 검토를 함께 사용하는 것이 안전합니다.

두 시스템을 함께 쓰면 데이터 동기화, 장애 처리와 운영 비용도 증가합니다. 결합이 정확도를 실제로 개선하는지 평가한 뒤 도입해야 합니다.
{: .notice--warning}

## 선택 기준

### 벡터 DB를 먼저 검토할 질문

- 같은 단어가 없어도 의미가 비슷한 결과를 찾아야 하는가
- 텍스트, 이미지나 음성처럼 비정형 데이터가 중심인가
- “이 항목과 가장 비슷한 상위 K개”가 핵심 질의인가
- RAG나 유사 콘텐츠 추천이 주요 기능인가

### 그래프 DB를 먼저 검토할 질문

- 여러 단계를 거친 연결 경로가 핵심인가
- 관계의 종류, 방향과 속성 자체가 중요한가
- 친구의 친구, 공통 기기, 의존성처럼 가변 길이 탐색이 많은가
- 결과가 선택된 관계 경로를 설명해야 하는가

### 기존 관계형 DB로 충분한지 확인할 질문

- 데이터와 질의 규모가 현재 DB에서 충분히 처리되는가
- 단순 JOIN, 전문 검색이나 벡터 확장으로 요구를 해결할 수 있는가
- 새로운 저장소를 추가했을 때 동기화와 장애 대응 비용을 감당할 수 있는가
- 실제 데이터로 정확도와 지연 시간을 측정했는가

## 도입 전에 측정할 것

### 벡터 검색

- 정답 후보가 검색 상위 K개에 포함되는 비율
- 검색 지연 시간과 처리량
- 임베딩·인덱스 생성 시간과 저장 비용
- 메타데이터 필터 적용 후의 recall
- 임베딩 모델 교체와 재색인 절차
- 사용자·tenant 간 데이터 격리

### 그래프 탐색

- 자주 사용하는 경로의 길이와 분기 수
- 시작 노드를 찾는 인덱스와 제약 조건
- 탐색 깊이를 제한하지 않았을 때의 비용
- 노드와 관계의 증가율 및 갱신 빈도
- 관계의 출처, 시점과 삭제 전파 방식
- 결과 경로를 감사하고 설명할 수 있는지 여부

데모 데이터 몇 건에서 빠르다는 사실만으로 제품을 선택하면 안 됩니다. 실제 분포와 권한 조건을 반영한 데이터로 정확도, 최악 지연 시간, 장애 복구와 운영 비용을 함께 검증합니다.

## 정리

벡터 DB는 임베딩 사이의 거리를 이용해 **의미나 특징이 비슷한 데이터**를 찾는 데 적합합니다. 의미 검색, RAG, 이미지 검색과 유사 추천에서 강점을 보이지만 검색 결과는 확률적 유사성에 가까우며 정확한 사실 관계를 보장하지 않습니다.

그래프 DB는 노드와 관계를 직접 저장해 **연결 구조와 경로**를 찾는 데 적합합니다. 사기 탐지, 지식 그래프, 권한, 추천과 의존성 분석에 유용하지만 의미 있는 관계 데이터를 먼저 설계하고 지속해서 관리해야 합니다.

둘 중 하나를 유행에 따라 고르기보다 서비스가 자주 묻는 질문을 살펴보는 것이 출발점입니다. 질문이 “무엇이 비슷한가”라면 벡터 검색을, “어떻게 연결됐는가”라면 그래프 탐색을 검토하세요. 두 질문이 모두 중요할 때만 결합 구조의 추가 복잡도를 감수할 가치가 있는지 측정하면 됩니다.
